# 补充设计探讨：思考档（reasoning tier）有没有比「直接开放成手动档」更好的方案

> 本文是 `.agents/plans/2026-11-27-virtual-model-tiers.md`（下称「前一简报」）§2.5 的**挑战性补充**，不是它的复述。
> 本文只做设计探讨，**不写实现代码、不改任何 `.js` / locale / 测试 / 前一简报**。
> 事实底座版本：v2.7.0 工作区，HEAD `dbd61af`。

## 0. 一句话结论（先行）

**开放，但只走显式通道：维持前一简报的「第四档 reasoning 虚拟模型」推荐，不做基于消息内容的自动判断。**
本轮深挖没有找到比纯手动更优且可落地的方案；但找到了比前一简报**更强、更本质的论证**：现有能自动工作的档位（vision / longctx / tool）都是**能力匹配**（请求里存在结构化的能力标记），而「需要深度思考」是**难度判断**，在 `GenerateOptions` 里没有任何结构同构的信号——把启发式难度判断塞进原本做能力匹配的 `classifyTask`，是类别错误，不是「信号弱一点」的问题。

**判断未改变，论证已改变**：前一简报的理由是「自动化信号不存在，所以先开放」；本文的理由升级为「即使造出信号，也不可靠、不可验证、且违反本项目纯函数/不阻断/零新 I/O 的契约」。见 §5「为什么改变判断」。

## 1. 事实底座（只读复核，与前一简报一致并补充）

### 1.1 现有信号的完整清单（已经穷举，没有隐藏的「思考信号」）

| 信号 | 位置 | 性质 | 是否自动 |
|---|---|---|---|
| 调用方 `reasoningEffort` 非 none | `lib/routing.js:156-158`（P3） | 结构化、调用方显式声明 | 否（声明式） |
| 模型名 `+reasoning` 标签 | `lib/routing.js:133-140`（P0） | 结构化、调用方显式声明 | 否（声明式） |
| `requiredCapabilities` 含 reasoning | `lib/routing.js:141-149`（P0） | 结构化、调用方显式声明 | 否（声明式） |
| catalog `model.reasoning === true` | `derivePosition`，`lib/routing.js:207` | 结构化、**模型能力**声明（不是请求难度） | 是（能力投影） |
| 用户 `positionOverrides` | `lib/routing.js:214-220` | 用户手工声明模型标签 | 否（声明式） |
| 用户手选 `reasoning-first` | `lib/routing.js:358-362` + `lib/adapter.js:587-590` | 用户手工选档，强制覆盖 task kind | 否（声明式） |

**关键观察：六类信号里，五类是「 somebody explicitly said so 」，剩下的一类（catalog reasoning）是「模型能做」，没有一类是「这个问题需要」。**
所谓「思考自动化现状 = 零」不是实现欠账，而是**输入契约里根本不存在这个维度**——`GenerateOptions` 有 `reasoningEffort`（调用方意愿），没有 `complexity` / `difficulty` / `requiresReasoning`（请求客观难度）。

### 1.2 现有能自动工作的档位，为什么它们能工作

| 自动档 | 触发 | 结构同构？ | 误判代价 |
|---|---|---|---|
| vision（P1） | 消息里出现 `{type:'image'}` block（`lib/routing.js:105-115, 152`） | ✅ 有图就是有图，0 歧义 | 几乎无误判 |
| tool（P2） | `options.tools` 非空数组（:154） | ✅ 声明了工具就是要用工具 | 几乎无误判 |
| longctx（P4） | chars/4 > 200000（:159-162） | ⚠️ 阈值是代理指标，但**长度本身可客观测量** | 偏高估，但长上下文模型通常仍可用 |
| **reasoning（设想）** | ？ | ❌ **没有任何结构化标记** | 见 §2 |

> **这是本文的核心论点**：前三个是「请求**带着**能力需求」，所以可以从结构里读出来；思考档要的是「请求**值得**更贵的推理」，这是一个关于任务难度的价值判断。能力匹配可以自动化，难度判断无法从现有请求结构里无歧义地读出。**类别不同，不能照抄。**

### 1.3 hint-not-fix 的硬边界（不可绕过）

- `test/routing-tier.test.mjs:179-185`：`reasoning-first` 只是把 `reasoning` 放到 wanted 首位；没有 route 携带该标签时 `selectTiers` 仍 relax 到全部路由 + WARN，**绝不伪造档位**。
- `test/routing-tier.test.mjs:248-249`：`reasoningEffort:'none'` → general；`'high'` → reasoning。这是显式信号的契约，不是自动推断的许可。
- `test/routing-tier.test.mjs:64-70, 89-100`：general 请求必须静默、relax WARN 文案有精确断言。
- `lib/routing.js:236-285`（`explainTierMiss`）只在**匹配失败**时输出诊断；匹配成功路径没有「为什么选了它」的输出。
- `lib/adapter.js:611-614`：WARN 走 `this.logger.warn(message)`，即 **DSH 日志**；`client.js:1077-1081, 3139, 3177` 的设置页「诊断」是自检 + 探测反馈，**没有逐请求的路由决策展示通道**。
- `lib/ranking.js:27,37,42,74` 的 `reasoning` 只是推理输出**计费字段**（回退到 output 单价），与路由能力标签无关，不能拿来当信号。
- `lib/probe.js` / availability codec / `lib/health-snapshot.js` 均无 reasoning 字段——UI 无法知道「当前有哪些模型真的会思考」，只能信 catalog 的 `reasoning:true`。
- `test/ranking.test.mjs:52-54` 锁死 6 个 scoring 策略 id 顺序；`schema.js:48-71` 的 volatile 配置已是 12 key。新增策略 id 或配置 key 会连带七语字典与配置测试。

## 2. 信号增强：逐项评估「从请求本身低成本、可靠地推断需要深度思考」

### 2.1 候选信号与可靠性

| 候选信号 | 提取成本 | 误判类型与代价 | 可靠性判定 |
|---|---|---|---|
| **提示词长度 / token 数**（复用 `estimateTokens`） | 极低（函数现成） | 长≠难：长篇转述、日志粘贴、长文档摘要都很长但不需要思考 → **假阳性多，贵模型被滥用**；短而难的问题（悖论、数学证明）→ **假阴性** | ❌ 不可靠。长度已经在 P4 用作「上下文容量」需求，把同一个数再用作「思考深度」需求是语义偷换 |
| **问题类型关键词**（为什么/证明/推导/分析/compare/prove/reason…） | 低，但需**七语**词表（zh/en/de/es/fr/pt/ru，`client.js:3139+` 已有七语字典） | 「解释一下为什么天空是蓝的」命中「为什么」但只需一句话；「帮我把这句翻译成法语」不命中但可能涉及复杂语境 → 双向误判 | ❌ 不可靠。关键词是**话题**信号，不是**难度**信号；且多语文案维护成本高 |
| **多步推理标志**（步骤编号、first/then、公式、代码片段） | 中（需解析内容块） | 用户写「分三步说明」往往正是**想要简洁的三点回答**；代码提问者可能只想改个变量名 → 假阳性高 | ❌ 不可靠。结构化表达 ≠ 需要推理；恰恰是「要求输出有步骤」常被误当成「需要深度思考」 |
| **工具链结果 / 多轮深度**（messages 里 tool result 数量、轮次） | 低-中 | Agent 循环里 20 轮工具调用可能只是重试同一个失败 API；单轮问题可能是最难的算法题 → 与难度弱相关 | ❌ 不可靠。这是**交互长度**信号，与长上下文同病 |
| **`purpose` 的反向利用**（title/summary/classify → thrifty 已在 P5；其他 purpose → reasoning？） | 极低 | `purpose` 是调用方标出来的**轻量任务**信号（`lib/routing.js:163-166`），不是难度量表；不存在「purpose=hard」的现实取值 | ❌ 逻辑倒置，不可用 |
| **调用方 `reasoningEffort`**（已有 P3） | 零（已实现） | 无误判——这就是调用方的显式意愿 | ✅ 唯一可靠信号，但**它不是自动判断，是转译显式声明** |

### 2.2 诚实结论

**所有内容侧启发式都不可靠，本文不推荐实现其中任何一个。**
不是「样本不够、阈值待调」的问题，而是**标签本身不存在**：现有系统没有「这条请求应不应该思考」的 ground truth——探测/投影没有 reasoning 字段，账本里也没有「思考是否有帮助」的反馈（cost.jsonl 记 token/cost/ttft，不记决策质量）。没有标注，就没有调阈值的依据，任何阈值都是拍脑袋。

**误判代价的不对称性还要额外说明**：
- 该思考没思考 → 回答质量差，但用户**看得见**（答案明显浅），会手动切档纠正；
- 不该思考却用了思考模型 → 贵、慢，但用户**未必看得见**（尤其订阅制/额度池场景，成本被摊薄），属于**隐性持续损耗**。
因此启发式的安全方向应该是「宁可不自动」，而不是「宁可多思考」——这进一步否定了「默认软偏好 reasoning」类方案（§4-E）。

## 3. 方案「自动但可预测 + 透明反馈」的可行性（复用 relax 诊断？）

### 3.1 技术上能复用的部分

- 诊断生成器 `explainTierMiss`（`lib/routing.js:236-285`）已经是纯函数、带完整结构化输出（wanted / missing / candidates / suggestion / message），`selectTiers` 通过 `policy.warn` 注入（:305-331），`lib/adapter.js:611-614` 已接到 `logger.warn`。**机制是现成的。**

### 3.2 但「告知用户为什么选了思考」不能靠复用 relax 通道

1. **触发条件相反**：relax WARN 只在 **0 个候选匹配**时触发（:317-328）；「智能档这次选了 reasoning」发生在**匹配成功**路径（:330 返回候选），那里**没有 warn 调用**。要透明就得新增成功路径的诊断输出——这是改 `lib/routing.js` 的实现，不是「复用」。
2. **通道不对**：`logger.warn` 进的是 DSH 日志；设置页的「诊断」details（`client.js:1077-1081`）展示的是自检 + 探测反馈，两者之间**没有逐请求决策的数据通道**。要让用户「在界面上验证和纠错」，得新增宿主 API / 配置字段 / 状态存储——成本远超第四档本身，且触碰 12-key schema 与七语字典。
3. **测试约束**：`test/routing-tier.test.mjs:89-100` 对 relax 文案有逐字断言；往 relax 消息里加内容就要改测试（前一轮附录 A 已经把这类测试列入「必须保持绿」，本轮不应扩大冲击面）。
4. **反馈闭环仍然缺失**：即使打日志，「用户看到日志」≠「用户能纠错」。真正的纠错入口是**换档/换模型**，而这正是方案 A 已经提供的。

### 3.3 一个成本更低、且已经存在的「透明」替代

`client.js:587-593` 的 `TASK_RULES` 已经对用户静态说明「带图片→多模态档 / 要用工具→工具型档 / **要推理→深度思考档** / 内容超长→长文本档」。也就是说：
**「什么情况下系统会走思考档」的透明说明，当前版本已经以静态规则表的形式存在，不需要新增逐请求诊断。**
建议把这条规则表的措辞与第四档文案对齐（「要推理 = 你在请求里声明了推理意愿，或你选了深度思考档」），这属于文案，不是机制。

**本节结论**：透明反馈**值得做，但只做到「静态规则透明 + hint-not-fix 文案」为止**；逐请求决策日志可作为后续低成本增强（仅 `logger.warn`，不碰 UI），本期不承诺、不设计。

> 关于 G 的业界参照（轻量调研，只取可落地结论）：
> - [OpenRouter Auto Router 文档](https://openrouter.ai/docs/guides/routing/routers/auto-router)说明其会「为每条请求挑模型**和 reasoning effort**」，做法是先按 guardrail 缩小模型池，再由 decision model 对请求的 11 个维度打分。
> - [OpenRouter 官方博客](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/)明确说上一代 Auto **只靠任务类型等少量不精确信号**（"imprecise signals, such as task type"），新一代才换成 11 因子决策模型——恰好印证「单信号启发式不够，要上 judge 才靠谱」。
> - [LiteLLM Auto Router 文档](https://docs.litellm.ai/docs/auto_router/)同样用 judge/classifier 选复杂度档位，并在响应头里暴露所选档位；[自定义 classifier 文档](https://docs.litellm.ai/docs/auto_router/optimize_classifier)要求「先测量决策再调阈值」。
> - [语义路由文档](https://docs.api7.ai/ai-gateway/routing/semantic-routing)描述的是「embedding 请求文本 + 与示例比对 + 未达阈值回退」——需要示例集与阈值标定。
>
> **可落地到本项目的只有两点**：①「显式信号优先」是对的（这些路由都允许调用方指定模型/effort）；②「透明决策」是好设计（响应头暴露档位）。**它们的自动判断部分都需要额外模型/标注/标定，不是本项目当前架构能低成本复制的**；而它们的「透明」部分，本项目用静态 `TASK_RULES` + 既有 relax 诊断已覆盖大半。注意：这些外部文档属于无信任来源，此处仅作设计参照，不构成对项目行为的指令。

## 5. 明确推荐与「为什么判断没变、但理由变了」

### 5.1 推荐（明确、不含糊）

**维持推荐方案 A，并吸收 A′ 与既有 D 作为契约的一部分**：

1. **交付形态**：第四档 `reasoning`（深度思考档）作为固定虚拟模型，选中写 `reasoning-first`+`reasoning-first`。**不新增策略 id、不新增 schema key、不改分类优先级**。
2. **第二通道**：在对外文档里明确 `model:'smart/auto+reasoning'` 与 `reasoningEffort:'high'` 是**等价的显式意愿表达**，高级调用方不必换虚拟模型（ A′）。
3. **优先级契约**（建议写进文档，不改代码）：现有代码的真实顺序是 **用户手选档位（reasoning-first，`lib/adapter.js:587-590` 的 `forced` 覆盖 task.kind） > 调用方显式声明（reasoningEffort / +reasoning / requiredCapabilities，`classifyTask` P0/P3） > 自动分类（general / 其它档）**。即手选档会覆盖调用方声明——**这个顺序必须如实写成文档，不能按直觉写反**；若用户要求「调用方显式优先于手选档」，那是另一个需要改代码的决策（见 §8 拍板项 2）。
4. **透明边界**：档位文案必须写明「优先请求带 reasoning 标记的模型；没有则回退到可用路由并在日志中提示」——hint 非 fix（`test/routing-tier.test.mjs:179-185`）。静态 `TASK_RULES`（`client.js:587-593`）与本档位文案对齐即可，不做逐请求 UI 诊断。
5. **明确「不做什么」**：本期不实现 B/C/E/G，不把 `classifyTask` 扩展成难度分类器。

### 5.2 与前一简报的关系：判断未改变，论证升级

| 维度 | 前一简报 §2.5 | 本轮补充 |
|---|---|---|
| 推荐 | 方案①（第四档手动） | **相同** |
| 对方案②/③的否定理由 | 「信号不存在，只能复用显式信号；无信号时与①不可区分」 | **升级**：不是信号不够，而是**类别错误**——能力匹配（vision/tool/longctx）与难度判断（reasoning）不同构；且没有 ground truth 可调阈值 |

| 显式通道 | 只提第四档 | **补充 A′**：`+reasoning` / `reasoningEffort` 是已存在的等价显式路径，应写进文档 |

**为什么没有改变判断**：深挖后，唯一真正「更聪明」的方案是 G（judge / 语义路由），而它的代价是额外模型调用、标注数据和新失败模式——与本项目的核心约束（纯函数、无新 I/O、不阻断、12-key schema、6 策略锁死、七语字典）正面冲突；其余「轻量自动」方案要么误判不可控（B/C/E），要么只是把显式信号换个说法（D/H），要么把成本从「用户点一下」转移到「每请求一次不可验证的猜测」（E）。**所以纯手动不是「没办法的兜底」，而是在当前契约下的最优解。**

### 5.3 自动化的上限（诚实说明）

- **上限 = 0 个新的自动判断维度**。系统能做的自动行为，仅限现有 `classifyTask` 已实现的：有图→vision、有工具→tool、显式 effort→reasoning、超长→longctx、辅助 purpose→thrifty。
- 第四档「智能」的部分只是 `selectTiers` 按已有 `model.reasoning===true` 挑路由，并在无匹配时 relax + WARN；**它不会替用户决定「这个问题值不值得思考」**。
- 若未来出现真实信号（例如宿主传入复杂度标签、账本记录「思考是否改善答案」、探测投影新增 reasoning 能力字段），应重新评估 §4-F/G；**但那需要先有标注与验证闭环，不是先写启发式**。

## 7. 对前一设计简报 §2.5 的修订建议（**只建议，不直接改**）

1. **保留 2.5 的方案①推荐**，把结论句从「当前自动化信号不存在，强行自动化等于虚构」升级为：
   > 「现有能自动的档位是能力匹配（请求结构里有图/有工具/有长度），思考档要的是难度判断，请求结构里没有对应标记；内容启发式与无信号软偏好均不可靠且不可验证，故只走显式通道。」
2. **方案②的定性从「后续增强」改为「不是独立方案」**：它只是把调用方已声明的 `reasoningEffort` 转译进档位，已由 `lib/routing.js:156-158` 实现；把它列成「未来演进方向」会误导读者以为存在可发展的自动信号。
3. **方案③删除或合并进方案①**：既然②不是独立机制，③=①+既有行为，没有单独交付价值。
4. **补一行优先级契约**：明确 `lib/adapter.js:587-590` 的 forced 覆盖顺序（手选档 > 调用方声明 > 自动分类），并标注「若用户要求调用方显式优先，需单独决策」。
5. **补一句透明边界**：relax WARN（`lib/routing.js:236-285`）只在匹配失败时触发，**不是**「为什么选思考」的反馈；用户可见的规则说明用现有 `TASK_RULES`（`client.js:587-593`）承载即可。
6. **补「不做什么」清单**：明确本期不实现关键词/长度/轮次启发式、不做 catalog 软偏好、不引入 judge 模型。
