# 根因分析：第二次打开设置页面空白

- 分析对象：`dsh-smart-provider` @ HEAD `9f50b71` / `v2.8.0`（工作树干净）
- 现象：第一次打开设置页正常；关闭后再次打开，Smart 智能路由页内容为空白
- 结论性质：**已定位到代码级根因，并有宿主运行日志直接印证**；不是推测
- 分析方式：只读静态分析 + 已安装 DSH 运行日志 + asar 内框架源码；未修改任何源码、未跑构建/测试/git 写操作

## 0. 一句话结论

`client.js` 的 `AccountsTab` 组件在渲染时引用了**不在其词法作用域内**的 `choices` 与 `strategy`（这两个变量只定义在另一个组件 `Overview` 内），必然抛 `ReferenceError: choices is not defined`；DSH 的 list 型 slot 错误边界捕获后把这个 `settings.section` 注册条目**永久 abdicate（从渲染投影中剔除，且不可恢复）**，因此第一次打开默认 overview tab 不触发该路径（正常），一旦渲染账号卡或第二次打开时崩溃一次，整个 section 就空白且再也无法恢复。

## 2. 设置页打开/关闭的完整调用链

### 2.1 注册（插件加载期，一次）

1. `client.js:21` 浏览器模块工厂执行；`:4681` 返回模块对象，`inject` 包含 `slots / locale / configForms / remote / remote.llm / remote.session / remote.settings`（`:4688`）。
2. `apply(ctx)`（`:4689`）：
   - `:4690` 注册 locale；
   - `:4694`–`:4710` `ctx.effect` 内异步 `$mount(makeCostContribution())` 挂 `remote.smartProvider`；
   - `:4712`–`:4739` 定义 `t()` 与 `injected()`（`injected()` 每次被 slot 调用时重新软读 `form` 与 `smartProvider`）；
   - `:4741` `ctx.slots.inject('settings.section', () => ctx.slots.register({...id:'smart-provider', inject: injected}, SmartSettingsSection))`；
   - `:4746` 注册 `settings.section.icon`；
   - `:4753`–`:4789` 对三个会话 slot 各自 `inject` + 根据 config 订阅注册 cost-pill。
3. 宿主侧 `dsh-client-ui-settings-general/src/client/index.ts:242` 声明的 `settings.section` 是 `list` 型 root slot。renderer `registry.ts:209` 的 `slots.inject` 在声明已存在时同步执行回调，于是 `SmartSettingsSection` 作为一条 entry 进入该 slot 的账本。**这一注册与设置面板的打开/关闭无关，面板关闭不会 dispose 它。**

### 2.2 打开设置面板

1. `SettingsRoot.tsx:258` `open && <SettingsPanel .../>`：打开时挂载 panel。
2. `SettingsPanel` `:109` 用 `renderSlot('settings.section', {close}, {only: active})` 渲染当前 active 的 section entry，`only: 'smart-provider'` 选中本插件条目。
3. `SmartSettingsSection`（`client.js:2712`）挂载：`tab` 初值 `'overview'`（`:2713`），`injected()` 提供 `form/remote/llm/session/costService` 等 props；多个 `useEffect` 异步读 pi 资源、availProjection、健康快照等。
4. render（`:3090`–`:3129`）按 `tab` 条件渲染：
   - `tab==='overview'` → `Overview`（`:3115`）；
   - `tab==='routing'` → `ChainsTab` + `AccountsTab`（`:3124`–`:3127`）；
   - `tab==='cost'` → `CostHealthTab`（`:3128`）。

### 2.3 关闭设置面板

`shell-store.ts:21` `close` 把 `open=false, activeId=undefined` → `SettingsRoot.tsx:258` 的 `{open && ...}` 分支消失，整棵 `SettingsPanel`（含 SmartSettingsSection）被 React 卸载；所有组件 `useEffect` 清理函数执行。但 `settings.section` slot 的声明与 entry **仍在账本中**（`slots.inject` 的 effect 属模块 apply 的 ctx，不随面板关闭结束）。

### 2.4 再次打开

重复 2.2。若该 entry 此前已被 abdicate，则 `entriesOfSlot('settings.section')` 投影（`slots/index.ts:1427`–`:1445`）不再返回它，panel 的 `.options` 区没有可渲染条目 → 内容空白（导航行液面仍有，因为 `settings.section.icon` 是另一条 slot entry；用户感受为「设置页内容空白」）。

## 3. 第一次 vs 第二次打开的差异点

| 维度 | 第一次打开 | 触发崩溃后 / 第二次打开 |
|---|---|---|
| `settings.section` entry 状态 | 正常在账本且未被 abdicate | 被 `reportEntryError(..., abdicate:true)` 加入 `WeakSet`，永久从投影中排除 |
| `entriesOfSlot('settings.section')` | 返回 `smart-provider` entry | 跳过该 entry → 无内容可渲染 |
| 组件是否重挂载 | 是，`SmartSettingsSection` fresh mount | 即使重挂载，entry 已在投影层被剔除，组件根本不会被渲染 |
| 可否自愈 | — | 不能：重复崩溃上报 no-op（`:1622`）；面板 close 不触发 slot 重新声明，故 `inject` 回调不会重跑来"重新注册"一条新 entry |
| 用户看到的默认 tab | overview（不渲染 AccountsTab） | 与上次 tab 无关：一旦崩溃即为空白 |

**纠正"第二次才空白"的字面理解**：严格说触发条件不是"打开次数"，而是"是否渲染过 `AccountsTab`"。默认 landing tab 是 overview，所以第一次打开通常正常；用户切到 routing tab 的账号卡（`client.js:3126`）时就会崩；崩过一次后，之后任何一次打开都空白。若用户第一次打开就点了 routing，第一次就会空白。日志时序与此一致（见 §4）。

### 4.3 为什么一次崩溃就永久空白（框架机制证据）

1. `dsh-client-ui-renderer/src/client/scoped-slots.tsx:1390`–`:1391`：`settings.section` 是 `list` 类 slot，`spec.kind !== 'chain'` 成立 → `reportEntryError(..., { abdicate: true })`。
2. `dsh-client-ui-slots/src/index.ts:1620`–`:1627`：首次上报 `this.abdicated.add(entry)` 并 `markDirty(key, rec)`；**重复上报直接 return（`:1622`）**。
3. `dsh-client-ui-slots/src/index.ts:1427`–`:1445`：`entriesOfSlot` 投影始终 `if (this.abdicated.has(entry)) continue`；注释 `:1061`–`:1065` 明确「for the rest of their registration's life」——注册条目仍在 ledger，但从渲染投影中被永久剔除。
4. `SettingsRoot.tsx:258`：面板关闭只卸载 React 子树；`shell-store.ts:21` 的 close 不动 slot 声明。renderer `registry.ts:209` 的 `slots.inject` 只在 declaration 变化时重跑回调。**关闭→再打开不会重新 register 一条新 entry**，旧的 abdicated entry 又不会自动复活 → 空白不可逆。
5. `SettingsRoot.tsx:109` 只有 `renderSlot('settings.section', ...)` 这一处内容渲染位；entry 被剔除后 `.options` 容器为空，用户界面即空白。

## 5. 建议的修复方向与影响面评估（仅供 lead/实现 agent 参考，本次不改代码）

### 5.1 最小修复（推荐）

删除 `client.js:1772`–`:1783` 整段 AccountsTab 内的重复「一键预设」按钮块。理由：

- 与 `:1754` 注释的既定设计一致（预设按钮只在 overview 保留一份）；
- overview 已有同款三按钮并接 `applyPreset`（`:995`–`:1006`），功能不丢失；
- 删除后 `AccountsTab` 不再引用 `choices` / `strategy`，ReferenceError 消失。

备选（不建议作为最小改动）：在 AccountsTab 内补上 `choices` 与 `strategy` 的局部定义。但这样会在账号卡里重复显示一套预设按钮，与注释和产品定调冲突，且还要正确计算 `strategy`（来自 `config.ranking.strategy`），改动面更大。

### 5.2 影响面

- **功能面**：零配置语义变化；仅删除视觉上的重复按钮。accounts 卡仍保留保存、删除、模型多选、ranking draft 等全部功能。
- **修复后行为**：新会话（或 HMR 重新 evaluate 模块并重新注册 entry）后，routing tab 与二次打开均正常；**已经 abdicate 的旧 entry 不会自愈**，需要刷新页面 / reload 插件使其重新 register，实现/验收时要说明这一点。
- **测试面**：现有单测是纯逻辑断言，无法捕获 JSX/组件渲染期的 ReferenceError（`node --check client.js` 语法检查也查不出未定义标识符，因为它们在运行时才解析）。建议在回归清单里补一条「浏览器里打开设置 → 切到路由/账号卡 → 关闭 → 再打开，内容不空」的手动/E2E 验证，或引入静态 lint（no-undef）覆盖 `client.js`。
- **同类隐患排查**：`AccountsTab` 之外暂无发现其他组件越界引用（grep `choices`/`strategy` 结果见 §4.2）；`conversation.input.right` 上的 `Minified React error #130`（日志 02:06、05:41）来自 conversation slot 里的对象作为 React 子节点，与本 bug 不同源，但会独立造成对话页 pill 空白，可另开单处理。
