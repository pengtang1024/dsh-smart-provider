# 账号池分级与多因素择优设计

> 任务：task-32（account-ranking）｜日期：2026-11-23｜**只设计，不改代码 / 不改生产配置**
>
> 用户需求原话：
> - 「账号池还要分级，不同的速率和价格（多种复合）要有一套择优原则」
> - 「价格还有多种情况，比如缓存命中，比如有的有缓存输出收费等等，不同的模型和提供商各种价格也不相同」
>
> 一句话结论：**保留现有「链选模型 → 池内选账号 → 失败按序降级」的两层结构，只在 `AccountPool.plan()` 的池内排序处插入一个可配置的线性评分器；价格按「分项定价表 + 账号覆盖 + 典型配比估算」计算，速率先手填，等级纯配置，未开启时行为逐字节不变。**

## 2. 数据模型扩展

### 2.1 Account 新增字段（全部可选）

| 字段 | 类型 | 默认 | 含义 | 谁填 |
|---|---|---|---|---|
| `tier` | `string \| number` | `'standard'` | 账号等级。`premium/standard/backup` 或 `3/2/1`（数字越大越高） | 用户手填 |
| `speedTier` | `'fast' \| 'normal' \| 'slow'` | `'normal'` | 速率档，手填。自动统计为 future | 用户手填 |
| `priceTier` | `'free' \| 'low' \| 'mid' \| 'high'` | `'mid'` | **兜底代理值**：定价表无该路由且用户未覆盖时用它参与成本评分 | 用户手填 |
| `priceMultiplier` | `number ≥ 0` | `1` | 相对单价乘数。`0` = 免费额度账号，`0.8` = 八折渠道 | 用户手填 |
| `priceOverrides` | `object` | `{}` | 分项单价覆盖，见 §3.2。既支持全局也支持按 model | 用户手填（可选） |
| `costModel` | `'metered' \| 'subscription' \| 'free'` | `'metered'` | 计费形态，决定成本因素取什么值，见 §4.3 | 用户手填 |
| `quotaCost` | `number ∈ [0,1]` | 缺省 | 订阅制的「额度消耗代价」代理值，越高越不愿用 | 用户手填（可选） |
| `priority` | `integer` | `0` | **硬优先级，数字越小越优先**（与 `tier` 方向相反！配置页必须提示） | 用户手填 |
| `weight` | `number ≥ 0` | `1` | 手动权重，乘在最终分上；`0` = 排最后但仍会被尝试 | 用户手填（可选） |

`id / provider / credentialRef / models` 四个基础字段含义不变。新增字段**非法时一律回落默认值，绝不丢弃账号**——延续 `normalizeAccounts` 现有的「非法项丢弃」风格只对基础字段生效。

## 3. 定价维度设计（用户补充需求的重点）

### 3.1 现有 pricing.json 核查结果

现有每条记录只有 4 个价格字段：

```json
{ "provider": "xiaomi", "model": "mimo-v2.6-flash",
  "input": 1.4e-7, "output": 2.8e-7, "cacheRead": 2.8e-9, "cacheWrite": 0 }
```

- ✅ 有：`input`、`output`、`cacheRead`（缓存命中输入）、`cacheWrite`（写缓存）
- ❌ 没有：`reasoning`（推理 token 单独计价）、`cacheOutput`（缓存输出单独计价）——正是用户点名的「有的有缓存输出收费」
- `null` 表示该路由不支持此项（如 `opencode-go/gpt-5.6-luna` 的 `cacheWrite: null`）
- 同一模型不同 provider 单价确实不同（例：`deepseek-v4.1-flash` 在 `opencode-go` 是 input `1.5e-7` / output `6e-7`，在 `opencode-zen` 是 input `3e-7` / output `1.2e-6`，**贵一倍**——表本身就是路由级，账号级差异必须能被覆盖）

**结论：不能改定价表结构（只读导出），但评分器要按「可扩展字段注册表」实现，UI 要能展示/编辑这些字段，缺的数据用户后续补。**

### 3.2 可扩展定价 schema（PRICE_FIELD_REGISTRY）

在 `lib/ranking.js` 导出一份**纯数据注册表**，评分循环和 UI 表单都从它读，新增字段不改评分公式：

| key | 中文名 | 表中现状 | 缺失时的 fallback | 说明 |
|---|---|---|---|---|
| `input` | 输入 | 有 | `0` | |
| `output` | 输出 | 有 | `0` | 通常比 input 贵 |
| `cacheRead` | 缓存命中输入 | 有，`null`=不支持 | `input` | 典型 0.1x |
| `cacheWrite` | 写缓存 | 有，`null`=不支持 | `input` | 部分厂商 1.25x~2x |
| `reasoning` | 推理输出 | **无，待补** | `output` | |
| `cacheOutput` | 缓存输出 | **无，待补** | `output` | 用户明确点名的场景 |

`resolvePrice(account, model, field)` 的优先级链（高→低）：

```
1. account.priceOverrides[model][field]   // 按模型的精确覆盖
2. account.priceOverrides[field]          // 账号级全局覆盖
3. priceFor(account.provider, model)[field]  // 定价表（provider+model 精确匹配，裸 model 兜最便宜）
4. P[field].fallback 对应的表字段          // 如 cacheRead 缺失 → input
5. 0
```

> `priceFor` 的裸 model 兜底会「取最便宜」（`pricing.js:56-63`），这对成本评分是保守估计：不会高估某个账号的贵程度。文档和 UI 都要提示 `known:false` 的账号是「无定价数据」，其成本分走 `priceTier` 代理值（§3.3）。

### 3.3 典型配比估算（评分用的「一次请求成本」）

评分不可能预测某次请求是否命中缓存、输出多长。务实做法：用**可配置的典型 token 配比**算一个稳定的相对成本。

```
blended(account, model) =
    Σ_{f ∈ PRICE_FIELDS} mix[f] × resolvePrice(account, model, f)
    ─────────────────────────────────────────────────────────────
                      Σ_{f ∈ PRICE_FIELDS} mix[f]
```

默认配比 `mix = {input:10, output:1, cacheRead:5, cacheWrite:1, reasoning:0, cacheOutput:0}`（概念上即用户举例的 10:1:5，写缓存按 1 份计）。分母只是缩放常数，不影响排序；保留它是为了让结果保持「每典型 token 的 USD」量纲，便于 UI 展示。

**手算示例**（`xiaomi / mimo-v2.6-flash`，取自 `pricing.json:1160-1173`）：

```
input=1.4e-7, output=2.8e-7, cacheRead=2.8e-9, cacheWrite=0
blended = (10×1.4e-7 + 1×2.8e-7 + 5×2.8e-9 + 1×0) / 17
        = 1.694e-6 / 17 ≈ 9.96e-8 USD / 典型 token
```

若该账号 `priceMultiplier = 0.9` → `8.97e-8`。`costModel: 'free'` 直接取 0。

### 3.4 计费形态：订阅制 / 免费 / 按量

| costModel | 成本因素取值 | 说明 |
|---|---|---|
| `metered`（默认） | `blended × priceMultiplier` | 真金白银 |
| `free` | `0` | 边际成本 0，成本分最高 |
| `subscription` | `quotaCost ?? normalizedBlended` | **额度是稀缺资源，用「额度消耗代价」代替价格**（用户诉求）。`normalizedBlended` = 该 model 候选账号 blended 值在当前归一化域内的 min-max 值（0..1）。用户填 `quotaCost` 可直接表达「这个订阅账号的额度更值钱/更不值钱」 |

补充：`quotaRemaining` 字段**本期只 schema 占位、不参与筛选**，作为 future 的硬健康源（额度耗尽 → 视为不健康）。别在本期实现，避免依赖外部额度 API。

### 3.5 历史账本反哺（能学什么，不能学什么）

**能学**：实际 token 配比（尤其缓存命中率、输出长度）。不同账号即使表价相同，真实成本画像也可能差很多。

设计（默认关闭，`historical.enabled: false`）：

```
observedMix[account][model] ← 最近 window 条 cost.jsonl 的
    {input, output, cacheRead, cacheWrite, reasoning, cacheOutput} token 总数归一
effectiveMix = (1 - mixWeight) × config.tokenMix + mixWeight × observedMix
blended 用 effectiveMix 计算
```

- `window` 默认 200，`mixWeight` 默认 0.3。
- 只读 `cost.jsonl` 的 token 计数字段，**不试图从 `estimated_cost_usd` 反推单价**。

**不能学**（明确写死在文档里，防止后续任务跑偏）：

- `estimated_cost_usd` 由同一份 `pricing.json` 算出（`cost-meter.js:78`），反推只会得到同一个表价，无法发现「这个渠道其实给我打了折」。
- 真实单价差异只能由 `priceMultiplier` / `priceOverrides` 提供；如果以后接了真实账单 API，再补 `observedUnitPrice` 字段。
- 延迟同样学不到：账本没有开始时间/时长（§1）。

## 4. 复合评分函数

### 4.1 五个因素

| 因素 | 原始量 | 方向 | 归一化方式 |
|---|---|---|---|
| **cost** | `effectiveCost`：§3.3/3.4 的 blended 或 quota 代理 | 越低越好 | 相对 min-max：`normLow(v, lo, hi) = lo===hi ? 1 : (hi-v)/(hi-lo)` |
| **speed** | `speedTier` 映射 `fast=1.0 / normal=0.6 / slow=0.2 / 未知=0.5` | 越高越好 | 绝对映射，已在 [0,1] |
| **tier** | `premium=1.0 / standard=0.6 / backup=0.2`；数字 `3→1.0 / 2→0.6 / 1→0.2`；未知 `0.5` | 见 `tierDirection` | 绝对映射；`tierDirection:'low'` 时 `1 - score` |
| **load** | `usage.get(accountId) ?? 0`（累计尝试次数） | 越低越好 | 相对 min-max `normLow`，最大值为 0 时全部 `1` |
| **health** | `isHealthy(accountId, now)` | — | **硬过滤，不进公式**：false 直接不出现在 attempt 列表 |

**归一化域 vs 候选域**（重要细节）：`cost` 与 `load` 的 `lo/hi` 取**该 model 下全部账号（含冷却中的）**，而最终排序只对**健康候选**进行。这样冷却变化不会让剩下账号的分数整体漂移，排序更稳定。

**退化规则**：`lo === hi` 时该因素返回 `1`（而不是 0.5）。原因：常数项对**所有候选加同一个值，不改变相对顺序**，比人为给 0.5 更不干扰其它因素。单账号场景同理。

### 4.2 公式

```
score(a, model, cfg, ctx) =
    max(0, a.weight) × (
        w_cost  × costScore(a, model, cfg, ctx)
      + w_speed × speedScore(a)
      + w_tier  × tierScore(a, cfg)
      + w_load  × loadScore(a, ctx)
    )
```

- `w_*` 来自策略预设或 `custom.weights`，**先归一化到和为 1**（UI 可让用户填任意非负数，显示归一化后的百分比）。
- `weight` 是账号级手动乘数，不参与权重归一化。
- 分数只用于**同一次 `plan()` 内的相对排序**，不做跨 model 比较。

### 4.3 排序分层（从外到内）

```
[priority hard 层] → [respectHopRoute 层] → [score 降序] → [tiebreak]
```

1. **priority 层**：`priorityMode:'hard'` 时按 `priority` 升序遍历层，一层用完再看下一层；`soft` 时 priority 不分层，只作最后的 tiebreak。
2. **route 层**：`respectHopRoute:true`（默认）时，账号 `provider === hop.provider` 的先试，保留现有语义；`false` 时跨 route 混排，让评分完全决定首选。
3. **score 降序**。
4. **tiebreak（固定顺序，保证确定性）**：`priority` 升（仅 soft）→ `usage` 升 → `id` 字典序升。

`weight = 0` 的账号分数为 0 排最后，但**仍在 attempt 列表中**——它是「最少使用」，不是「禁用」。要禁用就别把它配进 `accounts`。

### 4.4 手算示例（说明预设如何改变首选）

候选（同一 model，忽略 route 层）：

| 账号 | costScore | speedScore | tierScore | loadScore | weight |
|---|---|---|---|---|---|
| A（premium/fast/贵/常用） | 0.0 | 1.0 | 1.0 | 0.0 | 1 |
| B（standard/normal/中/少用） | 0.5 | 0.6 | 0.6 | 1.0 | 1 |
| C（backup/slow/便宜/没用过） | 1.0 | 0.2 | 0.2 | 1.0 | 1 |

| 策略 | A | B | C | 首选 |
|---|---|---|---|---|
| `balanced` (.40/.20/.15/.25) | 0.35 | 0.66 | 0.72 | **C** |
| `cost-first` (.70/.05/.10/.15) | 0.15 | 0.59 | 0.88 | **C** |
| `speed-first` (.10/.65/.10/.15) | 0.75 | 0.65 | 0.40 | **A** |
| `tier-first` (.10/.10/.65/.15) | 0.75 | 0.65 | 0.40 | **A** |

四套预设给出四种不同首选，说明单一 `tier` 字段无法表达用户需求，必须复合评分。

## 5. 策略预设表

| id | 名称 | cost | speed | tier | load | 适用场景 |
|---|---|---|---|---|---|---|
| `legacy` | 兼容模式 | — | — | — | — | 完全走现有比较器（route 优先 → usage 少优先），`enabled:false` 时的等价行为 |
| `balanced` | 均衡（推荐默认） | 0.40 | 0.20 | 0.15 | 0.25 | 日常自动模式，省钱但不牺牲太多速度 |

```
plan(chain, now):
  if (!this.configured) → 原样走 legacy 分支（account-pool.js:142-149），一行不动
  seenModels 去重逻辑原样保留（chain 决定 model 顺序，不变）
  对第一个 hop 的 model:
    domain  = accountsFor(model)                 // 全部账号，含冷却中，用于归一化
    pool    = domain.filter(isHealthy)           // 硬过滤，行为不变
    if (!ranking.enabled || ranking.strategy === 'legacy'):
        order = 现有比较器(aPreferred, usage)      // 逐字节不变
    else:
        order = rankAccountsForHop(domain, pool, model, hop, ranking, {usage, now})
    为每个账号生成 attempt（hop.provider 仍取 account.provider，行为不变）
```

必须保证的兼容点：

1. **无 `ranking` 配置 / `enabled:false`** → 现有比较器原路径，现有测试 `test/account-pool.test.mjs:81-114, 159-186` 全部不变。
2. **无 `accounts` 配置** → implicit 1:1 路径完全不碰。
3. **账号没填新字段** → 中性默认值（tier=standard、speed=normal、cost 从表价或 priceTier 代理），不会报错、不会因为「没配分级」就被排到最后。
4. **新增字段非法** → 回落默认值，不丢弃账号（与基础字段的 validate 策略不同，要刻意保持宽松）。
5. **失败降级路径不变**：`adapter.stream()` 依旧按 `plan()` 返回的列表顺序逐个尝试；评分只改变「谁排第一」，不改变「失败后继续往下试」的语义。

### 择优 vs fallback 的关系（一句话说清）

> **择优 = 每次请求开始时，为「模型链里的每个 model」生成一个按分数排好序的账号 attempt 列表；fallback = adapter 照着这个列表从前往后试，失败就下一个。分数决定优先级，不决定是否重试。**

- 模型之间的顺序仍由 `chains.js` 的 hop 顺序决定（评分**不重排模型**）；同模型的账号顺序由评分决定。
- 冷却中的账号在 `plan()` 阶段就被剔除；请求进行中某账号失败被设冷却，不影响本次已生成的列表继续尝试下一项（现有行为保持），下次请求才生效。
- 一旦有内容 chunk 吐出，仍按现有 establishment-only 规则锁定响应，不因评分而回退。
- 实现提示（非本期改动）：`plan()` 列表里同一账号可能在不同 model 下重复出现；若后续要在尝试前复查冷却，是新任务，别混进本次改造。

### 8.5 硬性前提：配置字段必须标 `.volatile()`（delivery-fix 实测反馈，已核验）

> 与配置页 agent（delivery-fix / task-31）对齐时发现的硬约束，已在本机 DSH 安装源码核实：DSH 的配置表单 `volatileForm(schema)` **只暴露 schema 里标了 `.volatile()` 的字段**；向非 volatile 路径写入会在 `dsh-settings` 抛 `Config field "xxx" is not volatile`。
> 证据：`/opt/DSH NEXT/resources/app.asar:2118084-2118099`（`volatileForm(schema)` → `isVolatilePath(schema, path)` 校验 → `configEditor.edit` 内 `validatePaths` 再校验）。

因此**后续实现任务在 `schema.js` 加字段时**，必须这样写（否则配置页看不到 / 保存被拒）：

```js
// schema.js —— 实现任务再改，本任务不动
ranking: z.any().default(undefined).volatile(),
```

同时注意现状：`chains` 与 `accounts` 目前是 `z.any().default(undefined)`（**非 volatile**，见 `schema.js:49,55`）。如果配置页要可视化编辑这两个区块，实现任务也需一并改成 `.volatile()`——但这属于「另一个交付物」的补救范围，由 delivery-fix 的方案界定；本文只负责把 `ranking` 的 volatile 前提钉死。`.volatile()` 的语义（热更新、不随配置版本冻结、编辑后立即生效）与本设计「改权重立刻影响下次请求」的预期一致。

两个 schema 常量保持**纯 JSON、零函数值**，UI 可直接消费；这一点已与 delivery-fix 确认，其方案 `两交付物补救方案.md` 按本契约消费，不另造字段。

## 10. 附：设计取舍自查

| 问题 | 回答 |
|---|---|
| 为什么分数用相对 min-max 而不是绝对价格档？ | 价格跨数量级（0 ~ 3e-5），绝对分档会丢失同档内的差异；同 model 内比较只需要相对序 |
| 为什么归一化域含冷却账号？ | 避免冷却变化导致剩余账号分数漂移，排序更稳定 |
| 为什么退化时给 1 而不是 0.5？ | 常数贡献不改变相对顺序，不会干扰其它因素 |
| 为什么速率不自动统计？ | 账本没有开始时间/时长（§1），硬做会引入猜测；手填档位足够表达用户意图 |
| 为什么不重排模型链？ | chain 是用户声明的 fallback 语义；评分只解决「同一个模型用哪个账号」 |
| 为什么价格要分项 + 配比？ | 用户点名缓存命中/缓存输出收费；单一 input 单价无法表达，分项 + 可配置配比既能覆盖又能稳定排序 |
| 为什么不从账本反推单价？ | 同源数据反推无新信息（§3.5）；诚实标注边界比假精确更有用 |
