# Intelligent Model Routing (Smart Provider)

A meta-provider registered as the `smart` route. It does not call any large-model API itself — instead it tries, in order, among your **already-configured DSH provider routes** and picks the first one that responds. It is a **general intelligent router**, not a cost-saving tool: the four goals are cost / performance / capability / composite (intelligent), and the code is neutral by default (balanced weight .25); cost-first is the user's own config choice.

**Status measured in this project's development environment (not a universal claim): the plugin is installed and enabled with status ACTIVE, and the host session has persisted the Smart virtual model; new installers should check their own profile.** Two default layers must be distinguished: **inside the plugin the default virtual model is Smart (`smart`) with default effort `auto`**, while in this development environment the **host session has persisted the Smart virtual model**: the profile's `agent-default-model` is `provider: smart` / `model: smart` (single-segment catalog id), effort is set by the `defaultEffort` setting (default `auto`), and `smart/auto` is only an internal combined id, not the value filled into the profile. Intelligent routing is effective by default; the cost-saving chain, real read/write settings page, P1 (resource adaptation / neutral default / dynamic chains), and P2 (two-layer intelligent routing, on by default with neutral equal weights, explicitly disableable) have all landed and been independently verified. The routing order follows your live registry and configuration, so this document does not hard-code any specific numbers.

## Features

- **Intelligent routing enabled by default.** The plugin-internal default is the Smart virtual model (`smart`) with default effort `auto`, with route selection and fallback verified in real sessions. New contract: **4 virtual models** (Balanced `balanced` / Economy `cost` / Efficient `speed` / Smart `smart`, Smart by default); **6 effort levels** (`auto` + Off `off` / Low `low` / Medium `medium` / High `high` / Max `max`, `auto` by default). The catalog lists only 4 single-segment models; effort is chosen independently via the `defaultEffort` setting — 24 combination ids are **not** catalog entries (internal parsing / legacy compatibility only). `auto` applies a **dynamic bias** from the chosen model plus task content, **not a hard model→effort mapping**; `classifyTask` keeps its intelligent judgement and a manual choice overrides auto. All four model names and six effort names go through 7-language locale keys `virtualModel.*` / `virtualEffort.*` (zh/en/de/es/fr/pt/ru); Chinese is no longer hard-coded. The built-in chain list is deliberately empty; when unconfigured, `discoverAutoChain()` generates a neutral `smart` chain from the live DSH registry (sorted by provider / model name, with no specific user's models built in).
- **Cost-saving chain (opt-in, not the default).** The free route `x-opencode-free` (`hy4-flash-free`) is automatically placed first in the chain by `tier: free` in `registry/custom-routes.user.yaml`; in the real ledger every transaction on this route has `estimated_cost_usd=0` (213+ entries verified); on 402/quota errors it falls back to a paid route. Since 2.3.0 the free-signal rule (`free-signal-v1`) treats a name containing `free`, `priceMultiplier=0` / `costModel=free` / `priceTier=free` as an **unmeasured, default-free weak signal** for admission / ranking / a "possibly free (unmeasured)" label only — never an L1 `billingTier=FREE`, and always overridable by probe `metered`, a positive-cost ledger row, or a paid `billingSource`. `unknown` never blocks a weak signal, an estimated zero price is not evidence, and the account price multiplier is editable in settings. Free labels come in three tiers — measured / declared / untested; measured labels now carry a source suffix ("confirmed free · price table / · probe / · ledger") and evidence is scoped to the `(provider, modelId)` tuple since 2.4.0 (no cross-provider name collision, no zero-price rows for `unavailable` registry entries); an account multiplier of 0 is declared-level and can be overturned by measured paid evidence. Many route probes still report `unknown`; the root cause remains [to be verified], so probing is not claimed to yield a verdict.
- **Account pool (multiple accounts = pooling).** Model and account are two independent dimensions. Each hop's model maps to an account pool (`{id, provider(route), credentialRef, models[]}`); healthy accounts on the current hop's route are preferred, then sorted by least-used; every healthy account for a model is tried before moving to the next model. DSH binds only one key per route, so a second account = a second provider route. The `accounts` array is optional; when unconfigured, behavior is byte-for-byte identical to the legacy version.
- **Account-level cooldown.** Cooldown is keyed by `accountId`, not `provider/model`. When one account hits a 402 or quota error, only that account is frozen; other accounts for the same model keep serving.
- **Three-layer health auto-management (on by default).** The model, account and topology layers keep separate records in one shared registry. Request-shape or missing-header 4xx errors never damage model health; a cooled account only becomes `HALF_OPEN` until a real request succeeds (`ACTIVE`); routes with their own account pools are not wrapped again (structural evidence only, no provider name allowlist). A one-token real probe replaces guessing free-vs-metered from model names, and an `unknown` verdict never blocks a route. Cold-start hydration (1.2.0) replays `cost.jsonl` and `probe-cache.jsonl` into the same L1/L2 registries (read-only, 4 MiB / 5000-line bounds, never overwriting newer live evidence). Explicit opt-out (`health: false` / `health.enabled: false` / `ranking.health.enabled: false`) returns byte-for-byte legacy and does not even open the ledgers.
- **Latency metering in `cost.jsonl`.** Each cost row may carry `started_at` / `first_token_at` / `finished_at` (ISO timestamps), `ttft_ms`, `duration_ms` and `tokens_per_second`; rows without these keys are simply omitted and old-row aggregation is unchanged. Both ranking and the cost page consume these derived metrics.
- **Query report (`scripts/query-cost.mjs`, two sections appended since 1.2.0).** The spend summary and per-group spend table are unchanged; after them come **failure rate** (`failed / calls` per group, only rows with a real `failure_code` count as failures) and **latency** (mean `ttft`, nearest-rank `p50`, ttft sample count, mean `tok/s`, tps sample count). Old rows without latency keys are excluded — never counted as 0ms; a real `ttft_ms=0` is still a valid sample; <3 samples gets `*`, no sample gets `-`, and a run with no samples prints an honest empty-state line; garbage values never yield `NaN`.
- **Pricing is user data.** The bundled `lib/pricing.json` contains only zero-price free-tier declarations (4 rows); real prices are imported via `DSH_SMART_PRICING_FILE` or `registry/pricing.user.json` (environment variable → user table → default table). Models with no price row resolve to a tier estimate (`known:false` / `estimated:true`, amount always 0); the author’s real price export remains an example at `lib/pricing.example.json`, outside the default load path.
- **Fallback only before establishment.** Once any text, reasoning, or tool-call chunk has been emitted, the response is committed — it will not fall back on tokens you have already seen; `ABORTED` never falls back.
- **Per-attempt session records.** Each attempt is written as an ignorable plugin record `plugin:dsh-smart-provider/hop-selected`, with payload `{event:'smart/hop-selected', hopIndex, provider, model, accountId, failureCode, at}`. This is the safe out-of-repository extension mechanism for `smart/hop-selected`: emitting an unknown event type directly would make session persistence refuse to restore the log.
- **Account ranking (P1, on by default).** Four-factor scoring of cost / speed / tier / load; `balanced` is the neutral default (.25), while `cost-first` and similar are explicit options; explicit `enabled:false` returns byte-for-byte legacy behavior (route priority + least-used).
- **Two-layer intelligent routing (P2, on by default).** `lib/routing.js` provides four pure functions: request classification, model position-tag derivation, candidate-tier selection, and preset resolution. It is on by default with neutral equal weights; explicit `ranking.routing.enabled=false` returns the legacy path byte-for-byte. 8 strategy presets: `balanced` / `cost-first` / `speed-first` / `reasoning-first` / `longctx-first` / `vision-first` / `legacy` / `custom`. Position tags are derived automatically from the model catalog (reasoning / contextWindow≥200000 / input contains image / tool!==false / general), and can be corrected manually with `positionOverrides`; a configuration error only emits a WARN and falls back to legacy, it does not crash.
- **Read-only model positioning on the settings page (phase 1).** The read-only note previously buried under "Routing settings → account pool → detailed settings → two-layer routing" is now shown prominently: three sentences (this is a read-only note, not an editable table; each model's position is derived from its own capabilities; individual models can be filled in manually) plus the four read-only task-recognition rules (**with an image → multimodal tier; needs tools → tool tier; needs reasoning → deep-thinking tier; very long content → long-text tier**). A new **per-model real positioning table** reads, through the new `@Remote` method `modelPositions()`, a Host-side pure projection (`adapter.routes` + `resolveModelInfo` capabilities + `positionOverrides`) and shows each model's position tags and source (`auto` / `user` / `mixed`). **Per-model capabilities come from the Host projection**: the `session.modelCatalog()` strict codec projects only `id/name/description/reasoning{efforts}/badge` — no `contextWindow` / `input` / `tool` — with reasoning proxied by `reasoning.efforts`; when the per-model data cannot be read, the table shows an "unconfirmed" empty state rather than fabricated rows. Both the static note and the table are read-only; **no manual-entry UI control is added** — manual overrides still go through `ranking.routing.positionOverrides` / `registry/position-overrides.user.yaml`.
- **Cost & health tab with real ledger data (the settings page has three tabs since 2.2.0: overview / routing / cost & health, merged from four; visual hierarchy compacted in 2.5.0).** The cost page reads, via the `@Remote` services `smartProvider.cost()` / `costDetail()` (`lib/remote.js`), the aggregation that `lib/cost-stats.js` computes over the real `cost.jsonl` (total spend / free / paid / failures / by provider) — not an estimated placeholder; the detail table carries the six latency fields plus ttft / tok-s columns, the cost trend buckets by **local calendar day**, and the settings page also shows the real provider / model and credential names from pi-ai. Since 2.5.0 the overview hero merges config facts with the health summary, preset buttons live only on the overview, the cost page folds detail / trend / ledger into an expandable block (Top 10 first screen), the health tables use summary rows plus expandable details (open by default on abnormalities), and the version line carries a GitHub star link; folding changes only information hierarchy, never the ledger channel or verdict rules.
- **Configurable conversation cost pill (2.4.0).** `costPillEnabled` defaults to `false`, `costPillPosition` defaults to `input.right` (also `conversation.session.header.utilities` and `conversation.input.dock`), and `costPillRefreshMs` defaults to 60000 ms with periodic monitoring off by default and a permanent manual "Refresh now" button. It reads the real ledger through `@Remote` `statsSince()`; "Reset stats from now" requires a second confirmation and only writes a new start marker in `stats-state.json` — `cost.jsonl` is never deleted. See the package README for details.
- **The native conversation effort control now appears (2026-11-28 wording).** `lib/tier-ids.js::virtualReasoningDeclaration()` declares six `reasoning.efforts` levels (`auto` + off/low/medium/high/max, default `auto`), and `lib/adapter.js` adds the `reasoning` field to smart entries in `listModels`/`resolveModel`, satisfying the host's `reasoning !== undefined` condition at `ModelSelect.tsx:498` — the native Effort row appears and users can pick a level in the same place as for other models. `auto` covers `off`: the default level omits the parameter and is decided dynamically by model plus task; a manual level unsupported by the first hop (the free hop only supports `off`) falls back to the legal `off` level rather than being sent as an unsupported high level. Native effort names are constrained by the host codec (`z.string()`): Chinese in the zh UI, English fallback elsewhere; the 7-language `virtualEffort.*` keys on the settings page stay intact. The earlier wording that the native control stays hidden and effort is set only on the settings page is obsolete; no routing-chain or first-hop change. See `SPEC-2026-11-27-smart-provider.md` §7.1.

## Installation

The install unit is a bundle: the marketplace installs the public npm package `dsh-smart-provider` (npm-first); for local development, `dsh plugin --profile <profile> add link:<this directory>` (or "Add plugin" in the UI) handles dependencies, bundle selection and the patch line together. A local directory is stored as `link:`, so source edits take effect without reinstalling; uninstall with `remove dsh-smart-provider`. After activation the host log should show `registered smart adapter with N chain keys` and `discovered N neutral auto hop(s)`. Runtime contract: only the `llm` service is hard-required; DSH packages resolve through manifest anchors, so a linked bundle works in any profile.

## Configuration

`chains`, `accounts`, `ranking`, and `ranking.routing` are all volatile settings; edits on the settings page take effect immediately with no restart. The routing config is nested under `ranking.routing` (schema.js:62-67), with fields: `enabled` / `strategy` / `tierPolicy` / `weights` / `positionOverrides` / `tierLimit` / `longContextTokens` / `dynamicAuto`. When not explicitly configured, the host injects default routing (`enabled:true` / `balanced` / four factors at .25); the legacy path is followed byte-for-byte only when `ranking.routing.enabled !== true` or is `null`. An explicit `chains` key and `*` always take priority over `dynamicAuto`, so legacy configurations are not affected. Each `accounts` pool entry has the form `{id, provider, credentialRef, models[]}`; when omitted, the legacy per-hop mode applies. Custom routes are declared only in `registry/custom-routes.user.yaml` (`credentialRef` holds only a reference name, never a plaintext key).

The detailed design is based on three documents in the parent workspace: `meta-provider-设计方案.md`, `多账号池设计方案.md`, `方案盲点审查.md`.
