# Intelligent Model Routing (Smart Provider)

A meta-provider registered as the `smart` route. It does not call any large-model API itself — instead it tries, in order, among your **already-configured DSH provider routes** and picks the first one that responds. It is a **general intelligent router**, not a cost-saving tool: the four goals are cost / performance / capability / composite (intelligent), and the code is neutral by default (balanced weight .25); cost-first is the user's own config choice.

**Current status: the plugin is installed and enabled, set as the default model, and the plugin status is ACTIVE.** Intelligent routing is effective by default; the cost-saving chain, real read/write settings page, P1 (resource adaptation / neutral default / dynamic chains), and P2 (two-layer intelligent routing, off by default) have all landed and been independently verified. The routing order follows your live registry and configuration, so this document does not hard-code any specific numbers.

## Features

- **Intelligent routing enabled by default.** `smart/auto` is the default model, with route selection and fallback verified in real sessions. The built-in chain list is deliberately empty; when unconfigured, `discoverAutoChain()` generates a neutral `auto` chain from the live DSH registry (sorted by provider / model name, with no specific user's models built in).
- **Cost-saving chain (opt-in, not the default).** The free route `x-opencode-free` (`hy4-flash-free`) is automatically placed first in the chain by `tier: free` in `registry/custom-routes.user.yaml`; in the real ledger every transaction on this route has `estimated_cost_usd=0` (213+ entries verified); on 402/quota errors it falls back to a paid route.
- **Account pool (multiple accounts = pooling).** Model and account are two independent dimensions. Each hop's model maps to an account pool (`{id, provider(route), credentialRef, models[]}`); healthy accounts on the current hop's route are preferred, then sorted by least-used; every healthy account for a model is tried before moving to the next model. DSH binds only one key per route, so a second account = a second provider route. The `accounts` array is optional; when unconfigured, behavior is byte-for-byte identical to the legacy version.
- **Account-level cooldown.** Cooldown is keyed by `accountId`, not `provider/model`. When one account hits a 402 or quota error, only that account is frozen; other accounts for the same model keep serving.
- **Fallback only before establishment.** Once any text, reasoning, or tool-call chunk has been emitted, the response is committed — it will not fall back on tokens you have already seen; `ABORTED` never falls back.
- **Per-attempt session records.** Each attempt is written as an ignorable plugin record `plugin:dsh-smart-provider/hop-selected`, with payload `{event:'smart/hop-selected', hopIndex, provider, model, accountId, failureCode, at}`. This is the safe out-of-repository extension mechanism for `smart/hop-selected`: emitting an unknown event type directly would make session persistence refuse to restore the log.
- **Account ranking (P1, off by default).** Four-factor scoring of cost / speed / tier / load; `balanced` is the neutral default (.25), while `cost-first` and similar are explicit options; when off, legacy behavior is preserved (route priority + least-used).
- **Two-layer intelligent routing (P2, off by default).** `lib/routing.js` provides four pure functions: request classification, model position-tag derivation, candidate-tier selection, and preset resolution. It activates only when `ranking.routing.enabled=true`; when unconfigured it runs the legacy path byte-for-byte. 8 strategy presets: `balanced` / `cost-first` / `speed-first` / `reasoning-first` / `longctx-first` / `vision-first` / `legacy` / `custom`. Position tags are derived automatically from the model catalog (reasoning / contextWindow≥200000 / input contains image / tool!==false / general), and can be corrected manually with `positionOverrides`; a configuration error only emits a WARN and falls back to legacy, it does not crash.
- **Cost & health tab with real ledger data (the settings page has three tabs since 2.2.0: overview / routing / cost & health, merged from four).** The cost page reads, via the `@Remote` services `smartProvider.cost()` / `costDetail()` (`lib/remote.js`), the aggregation that `lib/cost-stats.js` computes over the real `cost.jsonl` (total spend / free / paid / failures / by provider) — not an estimated placeholder; the detail table carries the six latency fields plus ttft / tok-s columns, the cost trend buckets by **local calendar day**, and the settings page also shows the real provider / model and credential names from pi-ai.

## Configuration

`chains`, `accounts`, `ranking`, and `ranking.routing` are all volatile settings; edits on the settings page take effect immediately with no restart. The routing config is nested under `ranking.routing` (schema.js:62-67), with fields: `enabled` / `strategy` / `tierPolicy` / `weights` / `positionOverrides` / `tierLimit` / `longContextTokens` / `dynamicAuto`. When unconfigured, the code path does not run at all; an explicit `chains` key and `*` always take priority over `dynamicAuto`, so legacy configurations are not affected. Each `accounts` pool entry has the form `{id, provider, credentialRef, models[]}`; when omitted, the legacy per-hop mode applies. Custom routes are declared only in `registry/custom-routes.user.yaml` (`credentialRef` holds only a reference name, never a plaintext key).
