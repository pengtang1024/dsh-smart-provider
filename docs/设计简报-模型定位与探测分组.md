# 设计简报：模型定位展示 + 免费模型探测分组

> 类型：头脑风暴设计简报（只做方案设计，不含生产代码、不改源码/配置/其他文档）
> 仓库：`dsh-smart-provider`，master，HEAD `20d46cf` / `v2.8.1`
> 时间：2026-11-27
> 输入：三份只读调研报告——`docs/现状调研报告-模型定位只读展示.md`、`docs/模型能力数据通路调研报告.md`、`docs/免费模型探测分组可行性调研报告.md`；表格宽度风险参考 `docs/样式问题调研报告-账号池表格.md`。
> 本简报中的「推荐」均为倾向性建议；第七章列出的澄清点**必须由用户拍板**，本简报不替用户决定。

## 1. 问题与目标

### 四问（用用户原文与调研结论回答）

**Q1：解决什么问题？**
用户原文诉求有两层：
1. 「这是只读说明，不是可编辑的表格」+「当前页面不读取逐台模型的定位结果」+「这个要想办法展示」——已存在的三句说明文案与四档识别规则（`client.js:587-593` `TASK_RULES`、`1519-1528` 渲染、`3237-3239` zh 字典，7 语齐全，`4678` 注册）被藏在「路由设置 → 账号池卡 → ⚙详细设置（默认折叠）→ 智能路由（两层）卡」深处（`client.js:1784`、`1911-1928`），普通用户看不到；且页面只渲染静态说明，没有逐台真实定位数据（`client.js:2952-2961` 的 `pi.models` 只有 `{id,name,group}`，`lib/remote.js:319-337` 无任何定位通道）。用户已明确选择「两者都要」：**既把静态说明提到设置页显眼位置，又展示逐台真实定位结果表**。
2. 「基于每台机器包含的模型可能不一样，建议如果有免费模型，选用一个用这个模型来判断一次本地模型分组」——想用现成的免费探测机制，按机器挑一个免费模型探一次，据此标记本地模型分组。机制现成（`lib/probe.js` + `@Remote probeModels` + `runProbe`/`probeVerdicts` + 7 天 TTL + `freeSignal`，见免费探测报告 §1），但**代码里没有「探测结果 → 分组」的字段或算法**（该报告 §3、§4）。

**Q2：为谁解决？**
Smart Provider 插件的设置页使用者：需要在设置页第一眼看懂「这个插件怎么识别任务、怎么给模型定位」的普通用户，以及希望看到**逐台真实定位结果**、并按机器了解「哪些是免费通道」的进阶用户。数据必须真实可读，读不到时明说读不到、不造假表（`client.js:1495`、`1519` 的产品纪律）。

**Q3：成功标准是什么？**
- S1：静态说明（三句文案 + 四档识别规则）在设置页显眼位置可见，不再默认折叠；只读性质不变。
- S2：设置页能展示**逐台真实定位结果表**，每行标明模型、定位 tags、`source: auto|user|mixed`，无真实能力证据的档位标「未确认」而非伪造。
- S3：探测分组能按用户确认的判定口径，按机器给出可解释的分组结论；`unknown` 不作结论、不否定弱信号。
- S4：两需求的正交关系被正确表达（定位=能力推导，分组=计费实测），不误导用户认为两者来自同一次探测。
- S5：改动全部在本仓库内、通过 `test/remote-surface.test.mjs:37` 的方法清单守卫与 7 语文案校验。

**Q4：有哪些已知约束？**
- 前端自算方案已**证伪**：Host `session/modelCatalog()` strict codec 只投影 `id/name/description/reasoning{efforts}/badge`（模型能力报告 §3.2-§3.3），无 `contextWindow/input/inputModalities/tool`，`reasoning` 是 efforts 对象；`client.js` 无 `derivePosition`、浏览器无法内联加载本地 ESM（`client.js:558-562`）。逐台定位表唯一确定路线是**方案 B：Host 新增 `@Remote modelPositions()`**（该报告 §5）。
- 重大隐患：`derivePosition()`（`lib/routing.js:205-224`）读 `reasoning===true`（:209）、`input` 数组（:211）、顶层 `contextWindow`（:210），与真实 Host 字段全错配；强推断运行期定位长期退化为 `[tool, general]`（模型能力报告 §2.3、§6.2）。
- 探测分组的**判定标准缺失是落地最大阻塞**（免费探测报告 §0、§5.1）。
- 两需求正交：定位表不依赖也不产生 probe 结果，不能共用同一次探测；仅展示层可复用（同一区域/`pi.models`，该报告 §6）。
- 静态说明是只读说明、**不是可编辑表格**；「个别模型可另外手填」是用户原文提到的既有能力方向（`README.md:389`、`lib/routing.js:176-194`、`index.js:234-279` 有 Host 配置/文件两路），但当前设置页**没有手填控件**（现状报告 §7.7）——是否纳入需澄清。

## 2. 方案分析

> 前提：逐台定位表的数据方案以「前端自算已证伪」为前提（模型能力报告 §0、§5），因此下列方案均**不列前端自算**；三方案差异在于**范围与呈现节奏**，而非数据通路。定位表数据通路统一采用 `@Remote modelPositions()` + Host 纯投影函数（模型能力报告 §5 方案 B）。

### 方案 A：分两期——先静态说明置顶 + 逐台定位表，探测分组另期

**思路**
一期交付用户已明确要求的「两者都要」（静态说明提到显眼位置 + 逐台真实定位表，走 `@Remote modelPositions()`）；探测分组因判定标准缺失，待用户拍板后再作为二期独立里程碑交付。

**优点**
- 严格对齐「用户已明确需求不推翻」：需求 1 完整交付，需求 2 的新想法不在标准未定时仓促落地。
- 逐台定位表与探测分组正交，分期不会造成架构耦合；一期的 codec/marker 改动可独立验证。
- 风险隔离：`derivePosition` 错配、Host contract 漂移等定位表风险在一期单独闭环，不被探测判定争议拖住。

**缺点**
- 用户提出的新想法（探测分组）不能同批看到，需要二次沟通与二次发版节奏。
- 若后续决定两区块并列展示，二期可能要回改一期的展示容器（改动小，仅限布局层）。

**适用场景**
探测判定口径短期无法拍板、或希望先拿到可验证的真实定位数据时。

---

### 方案 B：三合一——同一区域同时呈现逐台定位表与探测分组

**思路**
在设置页同一张表/同一卡片里并列展示「能力定位标签」列与「免费探测分组」列，一次到位交付两个需求；数据仍分开取（定位走 `modelPositions()`，分组走现有 `probeModels`/`probeVerdicts`），只共享展示容器与 `pi.models` 清单。

**优点**
- 用户一屏看全每台机器的「能力定位 + 计费分组」两个正交维度，信息密度高。
- 复用现有 `pi.models`、`probeVerdicts`（按 `group/model` 索引，`client.js:938`、`1057`、`1644`）与 `S.table`/`S.pill` 样式（`client.js:717-732`），展示层改动集中在一处。
- 一次设计、一次 i18n 补齐，减少两期之间的文案返工。

**缺点**
- **被最大阻塞卡住**：判定标准未定义前，分组列无法给出可信结论（免费探测报告 §5.1）。
- 同一张表叠加两列会让多语言文案更宽，触发刚修过的表格列挤压问题（`docs/样式问题调研报告-账号池表格.md`：`S.table` auto layout、`S.th/S.td` 无 nowrap/minWidth，`client.js:723-725`）。
- 用户可能误以为两列来自同一次探测，必须在 UI 明示「两个维度、两次独立过程」（免费探测报告 §6）。

**适用场景**
用户能立刻拍板判定口径、且希望一次交付完整体验时。

---

### 方案 C：最小——只把静态说明提出来，逐台表与探测分组暂缓

**思路**
仅把已有三句说明 + 四档规则从 `Advanced`（`client.js:1784`）提到显眼位置，不新增 `@Remote`、不展示真实数据。

**优点**
- 改动极小：复用现成 `RoutingForm` 两个只读块（`client.js:1519-1528`）与现有文案 key（`3237-3239`，7 语齐全），风险与测试面最小。
- 不触碰 strict codec / marker / 守卫常量，不受 Host contract 漂移影响。

**缺点**
- **不满足用户已选的「两者都要」**：逐台真实定位表被完全搁置，属于自行推翻已明确需求，不能作为最终推荐。
- 说明里「当前页面不读取逐台模型的定位结果」（`client.js:3238`）仍属实，用户的核心痛点未解决。

**适用场景**
仅作紧急止损/临时过渡；除非用户主动缩小需求，否则不采用。

## 4. 推荐方案 + 风险表

### 推荐：方案 A（分两期）

**推荐理由（3 点）**
1. **尊重已明确需求**：用户已选「两者都要」，方案 A 完整交付需求 1 的静态说明置顶 + 逐台真实定位表；方案 C 搁置逐台表属于推翻已定需求，不可取。
2. **阻断项解耦**：探测分组的最大阻塞是判定标准缺失（免费探测报告 §0/§5.1），与其让整期被卡住，不如把一期定位表（`derivePosition` 数据通路已确定可行）先交付验证，二期待用户拍板后接上。
3. **风险可控**：新增 `@Remote modelPositions()` 沿用 `accountHealth()` 的零参数 direct 范式（`lib/remote.js:311-316`），全部改动在本仓库；一期独立通过方法清单守卫与 7 语校验，二期探测分组可按路径 A（仅 `client.js`，最轻）起步，避免一上来就动新存储（免费探测报告 §4 路径 A/B/C）。

> 若用户在澄清点 1/2 立即给出判定口径，可将方案 A 的一、二期合并为方案 B 的一次交付——但**展示层两列必须明示「能力推导 vs 计费实测」是两个正交维度、两次独立过程**（免费探测报告 §6）。

## 6. 必须用户拍板的澄清点（逐条候选项 + 推荐倾向，不替用户决定）

> 以下每条均需用户明确选择后才能进入实现；「推荐倾向」只是设计侧建议，**不是决定**。

### 澄清点 1：探测结果 `free` / `metered` / `unknown` 分别判成哪个分组？（最核心、落地最大阻塞）
- **候选 A（按代表模型判定，最轻）**：每台机器挑一个免费候选探一次；`free` → 「含免费组/免费机」，`metered` → 「付费组」，`unknown` → 「未确认」（不否定弱信号）。复用 `probeVerdicts`，客户端即可实现（免费探测报告 §4 路径 A）。
- **候选 B（保守全量判定）**：机器上**所有**模型实测 `free` 才判「免费组」，否则一律「未确认/待核实」；误判率低但探测次数多、成本高。
- **候选 C（不做机器级分组）**：只给每个模型打免费/计费标签，不聚合到机器；分组需求降级为说明。
- **推荐倾向**：A，并把 `unknown` 显式单列；理由是与现有 `probeVerdict` 契约、`freeSignal` 等级阶梯（`lib/free-policy.js:17-18`）和「unknown 不作结论」纪律一致，改动最小。**请用户指定口径后才实现。**

### 澄清点 2：「每台机器」的边界 = provider/route（`group`）还是 `accounts[]` 条目？
- **候选 A**：`group`（`session.modelCatalog()` 的 provider/route id，`client.js:2959`；也是 probe 缓存的 `provider` 键）。数据现成、探测现成。
- **候选 B**：`accounts[]` 条目（`client.js` 另行维护，`accountDeclaredOf` `845-860`）。更贴近「账号池里的账号」，但与 modelCatalog 的 `group` 不一一对应，需要新的聚合/映射。
- **候选 C**：物理机维度（一台机器上的所有 provider），当前代码无对应概念。
- **推荐倾向**：A 起步（免费探测报告 §3.1），因为现有 `pi.models.group` 与 `probeVerdicts[group/model]` 都按 `group` 索引；若用户真实意图是 B/C，需追加聚合设计。

### 澄清点 3：`derivePosition()` 字段错配本次是否一并修？
- **候选 A（推荐倾向）**：修。`lib/routing.js:209-213` 读的 `reasoning===true`/`input`/顶层 `contextWindow` 与 Host 真实字段全错配（模型能力报告 §2.3），不修则逐台表长期显示 `[tool, general]`，M2 的展示价值归零；修正需在投影函数或 `derivePosition` 内兼容双形态并补单测。
- **候选 B**：不修，仅在表里标注「推导结果可能不完整」并展示原始能力字段，把修正留作独立任务。
- **推荐倾向**：A；除非用户希望把定位推导修正作为单独变更处理。

### 澄清点 4：「个别模型手填定位」是否纳入本次？
- **候选 A（推荐倾向）**：本次只保留现有说明文案（用户原文「个别模型可另外手填」，`client.js:3238`），不新增 UI 控件；手填继续走 `ranking.routing.positionOverrides` / `registry/position-overrides.user.yaml`（`README.md:389`、`index.js:234-279`）。
- **候选 B**：设置页新增手填控件（写 `positionOverrides`），属新功能，需表单/校验/保存/多语与测试，超出「只读展示」范围。
- **推荐倾向**：A；用户硬约束是静态说明只读、当前无手填控件（`client.js` 全文无该表单），B 应单独立项。

### 澄清点 5：逐台定位表与探测分组是否在同一区域并列展示？
- **候选 A**：同一区域两张卡/同一表两列（呼应方案 B）；须明示两维度正交、两次独立过程（免费探测报告 §6）。
- **候选 B（推荐倾向）**：先分两块（M2 定位表、M3 分组），保持数据通路与展示解耦；若用户后续要求并列再做布局调整。
- **推荐倾向**：B 起步；若用户选 A，需额外验收多语言列宽（风险 R4）。

### 澄清点 6：探测结果是否跨 reload 持久化（7 天 TTL 缓存复用？）
- **候选 A（推荐倾向）**：复用 `probe-cache.jsonl` 的 7 天 TTL（`lib/probe.js:37-46`），分组在读取时现算，不新增存储（免费探测报告 §4 路径 B 思路）。
- **候选 B**：新增按机器/账户维度的分组结果存储（如 `model-groups.jsonl` + 冷启动 hydrate），跨 reload 可见但改动最大（路径 C）。
- **候选 C**：不持久化，`probeVerdicts` 仅内存态，reload 后重新探测（路径 A，客户端没有 peek 通道，`lib/remote.js:319-337`）。
- **推荐倾向**：A；存量缓存已覆盖「最新一条胜出 + 冷启动回放」（`lib/probe.js:67-68`、`lib/health-persistence.js:273-332`），没必要新数据域。

### 澄清点 7：长文本阈值是否显示具体数字？
- **候选 A（推荐倾向）**：显示当前阈值（默认 200000，`lib/routing.js:27`、`162-164`；可由 `ranking.routing.longContextTokens` 覆盖，`README.md:391`），用 `fmt` 插值 `{n}`（`client.js:608-615`）；注意该字段目前**不在设置页表单里**（仅 `applyPreset` 注释 `client.js:3068` 提到保留），文案需说明「如已配置以配置为准」。
- **候选 B**：只写「内容超长」不写数字，保持与现有四档文案逐字一致（`client.js:588-593`、`3237-3239`）。
- **推荐倾向**：A（对进阶用户更有用），但需 7 语补齐插值文案；若用户重视与既有文案逐字一致则选 B。

> 另需用户确认（非阻塞主设计）：探测频率上限/开关（机器多时是否加 cap，风险 R7）、以及 `group==='smart'` 虚拟副本是否排除（`client.js:1171-1172`、`945`）——这两项可在 M3 细化时再定。
