# Интеллектуальная маршрутизация моделей (Smart Provider)

Мета-провайдер, зарегистрированный как маршрут `smart`. Сам он не вызывает никаких API больших моделей — вместо этого он по очереди пробует **уже настроенные вами маршруты провайдеров DSH** и выбирает первый, который ответил. Это **универсальный интеллектуальный маршрутизатор**, а не инструмент экономии: четыре цели — экономия средств / высокая производительность / широкие возможности / комбинированный (интеллектуальный) подход. В коде по умолчанию задана нейтральная позиция (сбалансированные веса .25); «приоритет экономии» — это осознанный выбор конфигурации пользователя.

**Состояние, измеренное в среде разработки этого проекта (не универсальное утверждение): плагин установлен и включён, статус ACTIVE, и сессия хоста сохранила виртуальную модель «Интеллектуальная»; новым пользователям следует проверить свой профиль.** Различайте два уровня значений по умолчанию: **внутри плагина модель по умолчанию — виртуальная модель «Интеллектуальная» (`smart`) с интенсивностью `auto`**; в этой среде разработки **сессия хоста сохранила виртуальную модель «Интеллектуальная»**: `agent-default-model` в профиле равен `provider: smart` / `model: smart` (односегментный идентификатор каталога), интенсивность определяется настройкой `defaultEffort` (по умолчанию `auto`), а `smart/auto` — лишь внутренний комбинированный идентификатор, а не значение, указываемое в профиле. Интеллектуальная маршрутизация действует по умолчанию; цепочки экономии, реальная запись и чтение на странице настроек, P1 (адаптация к ресурсам / нейтральные настройки по умолчанию / динамические цепочки) и P2 (двухуровневая интеллектуальная маршрутизация, по умолчанию включена и нейтральна, отключается явно) реализованы и независимо проверены. Порядок маршрутов определяется вашей актуальной реестровой базой и конфигурацией; этот документ не фиксирует конкретные числа.

## Возможности

- **Интеллектуальная маршрутизация включена по умолчанию.** Внутри плагина модель по умолчанию — виртуальная модель «Интеллектуальная» (`smart`) с интенсивностью `auto` (выбор маршрута и откат проверены в реальных сессиях). Новый контракт: **4 виртуальные модели** (Сбалансированная `balanced` / Экономичная `cost` / Эффективная `speed` / Интеллектуальная `smart`, по умолчанию Интеллектуальная); **6 уровней интенсивности** (`auto` + Выкл. `off` / Низкая `low` / Средняя `medium` / Высокая `high` / Максимальная `max`, по умолчанию `auto`). Каталог содержит только 4 односегментные модели; интенсивность выбирается отдельно через настройку `defaultEffort`, а 24 комбинации **не** являются записями каталога (только внутренний разбор и совместимость). `auto` задаёт **динамическое смещение** по модели и содержимому задачи, **а не жёсткое соответствие модель→интенсивность**; интеллектуальное решение `classifyTask` сохраняется, а ручной выбор перекрывает auto. Все четыре названия моделей и шесть названий интенсивностей идут через ключи локализации в 7 языках `virtualModel.*` / `virtualEffort.*` (zh/en/de/es/fr/pt/ru); китайский текст больше не жёстко задаётся. Встроенный список цепочек намеренно пуст; без конфигурации `discoverAutoChain()` создаёт из актуального реестра DSH нейтральную цепочку `smart` (сортировка по имени провайдера/модели, без жёстко встроенных моделей конкретных пользователей).
- **Цепочка экономии (необязательная, не по умолчанию).** Бесплатный маршрут `x-opencode-free` (`hy4-flash-free`) автоматически ставится в начало цепочки благодаря `tier: free` в `registry/custom-routes.user.yaml`; в реальном журнале расходов каждая запись этого маршрута имеет `estimated_cost_usd=0` (проверено 213+ записей); при ошибках 402/квоты происходит откат на платный маршрут.
- **Пул аккаунтов (несколько аккаунтов = пул).** Модель и аккаунт — два независимых измерения. Каждый переход цепочки сопоставляет модель с пулом аккаунтов (`{id, provider(маршрут), credentialRef, models[]}`); сначала выбираются исправные аккаунты на маршруте этого перехода, затем — менее использованные; перед переходом к следующей модели перебираются все исправные аккаунты текущей модели. Поскольку DSH связывает с каждым маршрутом только один ключ, второй аккаунт — это второй маршрут провайдера. Массив `accounts` необязателен; без конфигурации поведение побайтово совпадает со старой версией.
- **Задержка на уровне аккаунта.** Ключ задержки — `accountId`, а не `provider/model`. Ошибка 402 или квоты у одного аккаунта замораживает только его; другие аккаунты той же модели продолжают обслуживать запросы.
- **Трёхуровневое автоматическое управление состоянием (включено по умолчанию).** Уровни модели, аккаунта и топологии ведут раздельные записи в одном общем реестре; 4xx из-за формы запроса или отсутствующего заголовка никогда не портят состояние модели; охлаждённый аккаунт переходит из `HALF_OPEN` в `ACTIVE` только после реального успешного запроса; маршруты с собственным пулом аккаунтов не оборачиваются повторно (только структурные признаки, без списков имён провайдеров). Реальный зонд на 1 токен заменяет догадки «бесплатно/платно» по имени модели; `unknown` никогда не блокирует. Гидратация при холодном старте (1.2.0) воспроизводит `cost.jsonl` и `probe-cache.jsonl` в тех же реестрах L1/L2 (только чтение, границы 4 МиБ / 5000 строк, без перезаписи более свежих реальных данных). Явное отключение (`health: false` / `health.enabled: false` / `ranking.health.enabled: false`) побайтово возвращает legacy и даже не открывает файлы.
- **Измерение задержки в `cost.jsonl`.** Каждая строка расходов может содержать `started_at` / `first_token_at` / `finished_at` (ISO-метки), `ttft_ms`, `duration_ms` и `tokens_per_second`; строки без этих ключей просто опускаются, агрегация старых строк не меняется. Ранжирование и страница расходов потребляют эти производные метрики.
- **Отчёт запроса (`scripts/query-cost.mjs`, два раздела добавлены с 1.2.0).** Сводка расходов и таблица по группам не изменились; после них идут **failure rate** (`failed / calls` по группам; ошибкой считается только строка с реальным `failure_code`) и **latency** (среднее `ttft`, `p50` по nearest-rank, число образцов ttft, среднее `tok/s`, число образцов tps). Старые строки без ключей задержки исключаются — никогда не считаются за 0 мс; реальное `ttft_ms=0` остаётся допустимым образцом; <3 образцов помечаются `*`, отсутствие образца — `-`, а запуск без образцов печатает честное пустое состояние; мусорные значения никогда не дают `NaN`.
- **Цены — данные пользователя.** Поставляемая `lib/pricing.json` содержит только объявления нулевой цены (4 строки); реальные цены импортируются через `DSH_SMART_PRICING_FILE` или `registry/pricing.user.json` (переменная окружения → пользовательская таблица → таблица по умолчанию). Модели без строки цены получают оценку по уровню (`known:false` / `estimated:true`, сумма всегда 0); реальный экспорт цен автора остаётся примером в `lib/pricing.example.json`, вне пути загрузки по умолчанию.
- **Откат только до установления ответа.** Как только передан любой блок текста, рассуждений или вызова инструмента, ответ считается зафиксированным — уже показанные токены не отзываются; `ABORTED` никогда не вызывает откат.
- **Журнал сессий для каждой попытки.** Каждая попытка записывается в виде игнорируемой плагином записи `plugin:dsh-smart-provider/hop-selected` с полезной нагрузкой
  `{event:'smart/hop-selected', hopIndex, provider, model, accountId, failureCode, at}`.
  Это безопасный способ расширения за пределами репозитория для `smart/hop-selected`: прямая отправка неизвестного типа события заставила бы систему сохранения сессий отклонить восстановление журнала.
- **Ранжирование аккаунтов (P1, по умолчанию включено и нейтрально, отключается явно).** Оценка по четырём факторам: стоимость / скорость / уровень / нагрузка; `balanced` — нейтральные настройки по умолчанию (.25), `cost-first` и подобные — явные варианты; при отключении сохраняется старое поведение (приоритет маршрута + меньше использованный).
- **Двухуровневая интеллектуальная маршрутизация (P2, по умолчанию включена и нейтральна, отключается явно).** В `lib/routing.js` четыре чистые функции: классификация запроса, вывод меток позиции модели, выбор слоя кандидатов и разрешение предустановок. Включена по умолчанию (`ranking.routing.enabled=true`, `balanced`, четыре равных фактора .25); при `ranking.routing.enabled=false` код побайтово идёт по legacy-пути. Восемь предустановок стратегий: `balanced` / `cost-first` / `speed-first` / `reasoning-first` / `longctx-first` / `vision-first` / `legacy` / `custom`. Метки позиций выводятся автоматически из каталога моделей (reasoning / contextWindow≥200000 / входные данные содержат image / tool!==false / общая), их можно вручную исправить через `positionOverrides`; ошибки конфигурации лишь выводят WARN и откатываются к legacy, не вызывая сбой.
- **Доступная только для чтения панель позиционирования моделей на странице настроек (фаза 1).** Прежде скрытая глубоко в «Маршрутизация → пул аккаунтов → подробные настройки (по умолчанию свёрнуто) → двухуровневая маршрутизация» справочная заметка теперь вынесена на заметное место: три фразы (это описание только для чтения, а не редактируемая таблица; позиция каждой модели выводится из её собственных возможностей; отдельные модели можно задать вручную) плюс четыре правила распознавания задач (**с изображением → мультимодальный уровень; нужны инструменты → уровень инструментов; нужно рассуждение → уровень глубокого мышления; очень длинный контент → уровень длинного текста**). Дополнительно добавлена **таблица реальных позиций по каждой модели**: она читает через новый метод `@Remote` `modelPositions()` чистую проекцию на стороне Host (`adapter.routes` + возможности `resolveModelInfo` + `positionOverrides`) и показывает для каждой модели метки позиции и источник (`auto` / `user` / `mixed`). **Возможности каждой модели приходят из проекции Host**: strict codec `session.modelCatalog()` проецирует только `id/name/description/reasoning{efforts}/badge`, без `contextWindow` / `input` / `tool`, а уровень рассуждения выводится из `reasoning.efforts`; если данные по моделям недоступны, таблица показывает состояние «не подтверждено», а не выдуманные строки. И статическая заметка, и таблица доступны только для чтения; **никакого поля ручного ввода в интерфейс не добавляется** — ручные правки по-прежнему идут через `ranking.routing.positionOverrides` / `registry/position-overrides.user.yaml`.
- **Вкладка «Стоимость и состояние» с реальным журналом (на странице настроек с 2.2.0 три вкладки: обзор / маршрутизация / стоимость и состояние — объединены из четырёх).** Страница стоимости читает через сервисы `@Remote` `smartProvider.cost()` / `costDetail()` (`lib/remote.js`) агрегацию `lib/cost-stats.js` по реальному `cost.jsonl` (всего расходов / бесплатно / платно / ошибки / по провайдерам) — это не оценочные заглушки; в таблице подробностей есть шесть полей задержки и столбцы ttft / tok-s, динамика расходов группируется по **локальному календарному дню**, а на странице настроек также показаны реальные провайдеры/модели и имена учётных данных из pi-ai.

- **Нативный элемент управления интенсивностью в диалоге теперь отображается (версия 2026-11-28).** `lib/tier-ids.js::virtualReasoningDeclaration()` объявляет шесть уровней `reasoning.efforts` (`auto` + Выкл. `off` / Низкая `low` / Средняя `medium` / Высокая `high` / Максимальная `max`, по умолчанию `auto`); `lib/adapter.js` добавляет поле `reasoning` записям smart в `listModels`/`resolveModel`, чем выполняется условие хоста `reasoning !== undefined` в `ModelSelect.tsx:498` — нативная строка Effort появляется, и пользователь может выбирать уровень в том же месте, что и для других моделей. `auto` включает `off`: уровень по умолчанию опускает параметр и определяется динамически по модели и задаче; ручной уровень, не поддерживаемый первым переходом (бесплатный переход поддерживает только `off`), понижается до допустимого уровня `off`, а не отправляется как неподдерживаемый высокий уровень. Нативные названия effort подчиняются codec хоста (`z.string()`): китайский в интерфейсе zh, английский как запасной вариант в остальных языках; 7-язычные ключи `virtualEffort.*` на странице настроек остаются без изменений. Прежняя формулировка о том, что нативный элемент скрыт, а интенсивность задаётся только на странице настроек, устарела; цепочка маршрутизации и первый переход не меняются. См. `SPEC-2026-11-27-smart-provider.md` §7.1.

## Установка

Единица установки — пакет (bundle): маркет устанавливает публичный npm-пакет `dsh-smart-provider` (npm-first); для локальной разработки `dsh plugin --profile <profile> add link:<этот каталог>` (или «Добавить плагин» в интерфейсе) вместе обрабатывает зависимости, выбор пакета и строку patch. Локальный каталог сохраняется как `link:`, поэтому изменения исходников действуют без переустановки; удаление — `remove dsh-smart-provider`. После активации в журнале хоста должны появиться `registered smart adapter with N chain keys` и `discovered N neutral auto hop(s)`. Контракт запуска: обязателен только сервис `llm`; пакеты DSH разрешаются через якоря манифеста, поэтому связанный пакет работает в любом профиле.

## Способы настройки

`chains`, `accounts`, `ranking` и `ranking.routing` — volatil-конфигурации; изменения на странице настроек вступают в силу сразу, без перезапуска. Конфигурация routing вложена в `ranking.routing` (schema.js:62-67), поля: `enabled` / `strategy` / `tierPolicy` / `weights` / `positionOverrides` / `tierLimit` / `longContextTokens` / `dynamicAuto`. Без явной конфигурации хост внедряет маршрутизацию по умолчанию (`enabled:true` / `balanced` / четыре фактора по .25); только при явном `ranking.routing.enabled !== true` или `null` путь кода побайтово следует legacy. Явный ключ `chains` и `*` всегда имеют приоритет над `dynamicAuto`, поэтому старые конфигурации не меняются неожиданным образом. Каждый элемент пула аккаунтов `accounts` имеет вид `{id, provider, credentialRef, models[]}`; при отсутствии конфигурации работает старый режим «на переход». Собственные маршруты объявляются только в `registry/custom-routes.user.yaml` (`credentialRef` содержит исключительно имя ссылки, никогда не открытый ключ).

Подробное обоснование приведено в трёх документах родительского рабочего каталога: `meta-provider-设计方案.md`, `多账号池设计方案.md`, `方案盲点审查.md`.

## Краткая справка (второстепенная)

Мета-провайдер, зарегистрированный как маршрут `smart`, **установлен и включён в среде разработки этого проекта** (новым пользователям следует проверить свой профиль); внутри плагина по умолчанию виртуальная модель «Интеллектуальная» (`smart`) с интенсивностью `auto`, тогда как модель по умолчанию сессии хоста теперь установлена на виртуальную модель «Интеллектуальная» (`agent-default-model` = `provider: smart` / `model: smart`, односегментный идентификатор каталога; интенсивность через `defaultEffort`, по умолчанию `auto`; `smart/auto` — лишь внутренний комбинированный идентификатор, а не значение профиля). Это универсальный интеллектуальный маршрутизатор (стоимость / скорость / возможности / комбинированный), в коде нейтральный по умолчанию; приоритет экономии — включаемая пользователем конфигурация. Проверено: виртуальная модель «Интеллектуальная» (`smart`) с интенсивностью `auto` в реальных сессиях (4 виртуальные модели, 6 уровней интенсивности, 4 односегментные записи каталога плюс настройка `defaultEffort`; `auto` — динамическое смещение, а не жёсткое соответствие; названия через ключи локализации в 7 языках), бесплатный первый переход `x-opencode-free` (cost=0, 213+ реальных строк журнала) с откатом 402→платный, страница настроек с реальными ресурсами pi-ai, вкладкой стоимости с журналом через `@Remote` и доступной только для чтения панелью позиционирования моделей (статическая заметка с четырьмя правилами плюс таблица реальных позиций по моделям из новой проекции Host `@Remote modelPositions()`, недоступные данные отображаются как «не подтверждено», ручные правки по-прежнему через файлы конфигурации), P1-адаптация ресурсов и P2-двухуровневый маршрутизатор, включённый по умолчанию (`ranking.routing.enabled=true`, 8 предустановок, побайтовый legacy при отключении). Полную конфигурацию и команды проверки см. в README пакета.
