# 用户资源自适应设计（通用产品的资源来源层修正）

> 状态：只读设计稿（task-45）。本轮**不改任何代码/配置、不重启 DSH**。
> 用户原话：**「每个人的模型是不一样的，你不能把我的模型配比默认为所有人都是这样」**。
> 结论先行：**插件是通用产品，不是"我的账号配置的可执行版"。用户资源一律"运行时发现"或"用户自带"，内置默认只能中立——不带任何人的模型清单、价格表、偏好权重。**

---

## 0. 核心原则（写死在产品定义里）

1. **零预装用户数据**：插件包内不得含有任何特定账号的 provider/model 清单、定价、偏好权重。当前三处违反：
   - `lib/chains.js:19-24` DEFAULT_CHAINS 写死 `opencode-go/deepseek-v4.1-flash`、`glm-5.3-flash`、`mimo-v2.6-flash`、`xiaomi-token-plan-cn/mimo-v2.6-flash` —— 别人装上是 Claude/GPT/Gemini/Ollama，全悬空。
   - `lib/pricing.json:2-5` `_source: Bifrost config.db governance_model_pricing (2026-11-23)`、148 条 —— 我的账号导出价，别人价格完全不同。
   - `lib/ranking.js:55,72` `BALANCED_WEIGHTS {cost:.4, speed:.2, tier:.15, load:.25}` + `default:'balanced'` —— 把"省钱为主"烧成所有人默认。
2. **发现 > 声明 > 内置**：资源优先级 = ① DSH 运行时注册表发现（模型/能力）② 用户声明（chains / pricing 表 / 偏好 / custom-routes）③ 中立内置（空壳，不含用户数据）。
3. **中立默认**：内置策略权重不偏向任何单一目标；"省钱为主"是当前用户的**配置值**，不是代码默认。
4. **与既有三份文档的关系**：本文修正它们的"资源从哪来"，不推翻其机制——
   - 《通用智能路由能力设计.md》：能力标签从**用户实际 catalog** 生成，不是内置表；
   - 《自建路由统一管理方案.md》：`custom-routes.yaml` 是**用户声明自己特殊资源**的地方，不是预装我的 x-opencode-free；
   - 《账号池择优设计.md》：评分因素不变，来源改为用户模型 + 用户定价。

## 1. 模型从哪来（运行时发现，不硬编码）

### 1.1 候选池发现

- 数据源（**已验证可达**，证据）：
  - `ctx.llm.listProviders()` —— 返回所有 adapter route（`dsh-llm/src/index.ts:498-500`）；`index.js:155` 已实际调用过（smart-status 命令），证明本插件上下文里可达。
  - `ctx.llm.listModels(provider)` —— 逐 provider 列模型；`dsh-api-session-controller/lib/index.js:525,528` 的 `buildModelCatalog` 就是这么用的。
  - `ctx.llm.listConfigurableProviders()` —— 目录表，判断 route 是否可配置（`两交付物补救方案.md:7,19`）。
- 设计：插件初始化（apply）时拉一次候选池 `discoveredRoutes: Array<{provider, models: ModelInfo[]}>`，作为**只读快照**；配置变更（`loader/volatile-update`）或模型目录刷新时重拉。ModelInfo 取 `id/name/contextWindow/reasoning/input`（pi-ai `types.d.ts:653,667,675`，能力来自用户实际 catalog，见《通用智能路由能力设计》§3.1）。

### 1.2 没配 chains 时：动态 auto 链

- 现状问题：`normalizeChains(undefined)` 返回写死的 DEFAULT_CHAINS（chains.js:46-48）→ 悬空引用。
- 改为：`chains` 未配置时，`resolveChain('auto')` 走**动态生成器**——从候选池按当前策略（§3）排序生成 hops，例如中立默认下按 provider 顺序 + context/能力匹配，不偏向任何账号。
- 显式模型键（如用户选了 `gpt-5`）仍按用户配置；未配置的显式键不预生成（不塞假模型）。
- 动态链是**计算值不落盘**：不写回用户配置，用户一旦显式配 chains 就完全覆盖它（向后兼容）。

### 1.3 空/新环境

- 候选池为空（无任何 provider）：`auto` 返回空链 → adapter 现有逻辑已能诚实报错（`adapter.js:285-294`，`UNKNOWN_MODEL`），不塞假模型。
- 配置页首屏显示诚实空态："未发现任何模型路由，请先在 DSH 设置→模型里添加" + 引导链接；配了 provider 后才让选策略。
- **未验证**：新装 DSH 的"零 provider"状态实际是否可到达（本机已有多个 provider，无法在本环境实测空态），落地时用全新 profile 验证。

## 2. 定价从哪来（不预装我的价格）

`pricing.json` 降级为**示例/可选导入**，不再作为产品数据。用户侧三种来源，按优先级：

1. **用户导入定价表**（主路径）：用户把自己的价格表放 `registry/pricing.yaml`（或配置页粘贴 JSON），结构沿用 `{provider, model, input, output, cacheRead, cacheWrite}`（兼容现有 pricing.js:43-75 的 priceFor 查找逻辑，改读用户文件即可）。
2. **无定价时按档位粗估**：`free / low / mid / high` 四档代理价（复用 `ranking.js:32,100` 的 `PRICE_TIERS` / `PRICE_TIER_PROXY` 思路），用户可对每个模型手填覆盖。粗估只用于排序，**不宣称精确成本**。
3. **账本反哺真实 token 配比**：cost-meter 已有按 attempt 的 token 记录（cost-meter.js:79-96）；从用户自己的历史用量算 input/output/cache 比例（`ranking.js:41 DEFAULT_TOKEN_MIX` 改成从用户账本算），这是"配比"不是"单价"，不涉及导出别人的价格。

- 迁移：当前 `pricing.json` 148 条作为**示例**移到 `registry/pricing.example.json`，导入时用户确认后再生效；不确认就不加载。
- **未验证**：用户导入表的校验规则（字段/单位）需落地时定，本稿只给结构方向。

## 3. 偏好从哪来（不烧我的）

### 3.1 中立默认

- `DEFAULT_RANKING_CONFIG`（ranking.js:57-66）改成真正中立：`strategy` 保留 `balanced` 作为**分类名**但权重四因素等分 `{cost:.25, speed:.25, tier:.25, load:.25}`；或直接新增 `neutral` 预设为默认。`cost:.4` 从 BALANCED_WEIGHTS（ranking.js:55）移除。
- 更关键：`enabled:false` 现状（ranking.js:58）意味着**默认不启用择优**，这本身就是中立——只需保证一旦用户启用，默认权重不偏 cost。
- "省钱为主"改成**当前用户的配置值**：由用户写入自己的 config，不由代码带出。

### 3.2 首启小白向导（三选一，写用户 config）

- 触发：`Config.chains`、`Config.accounts`、`Config.ranking` 全部为空（= 新用户）时，配置页首屏显示大白话三选一：
  - 「省钱优先」→ 写 `ranking.strategy=cost-first`
  - 「速度优先」→ `speed-first`
  - 「均衡（推荐）」→ `balanced`（中立权重）
- 选择写入**该用户的 volatile config**（现有 configForms 通道，client.js:582 mutate），可随时改；未选前保持中立/不启用，不替用户决定。
- 不写死在代码默认里；老用户有配置则不弹向导（平滑迁移）。

## 4. 与现有机制的关系（兼容，不推翻）

| 机制 | 从 | 改为 | 兼容保证 |
|---|---|---|---|
| custom-routes.yaml | 预装我的 x-opencode-free | 用户声明自己特殊资源的空模板/示例 | 已有 route 作为"当前用户配置"保留，新用户是空模板 |

| pricing | 148 条导出价 | 示例 + 用户导入 + 档位粗估 | 旧 pricing.json 改名 example，不自动加载 |
| 策略权重 | balanced cost:.4 | 中立等分 + 首启向导 | 老配置 strategy 值原样保留 |

## 5. 迁移方案（当前用户不丢）

1. **配置优先**：`Config.chains` 已有值（当前用户 cordis smart config.chains 里 auto 首跳 x-opencode-free）→ 照常使用，动态生成只在未配置时兜底。
2. **pricing**：把现有 `pricing.json` 复制为 `registry/pricing.example.json`，产品包内不再默认加载；当前用户若想继续用，显式导入一次（写进自己配置）。
3. **偏好**：当前用户已有的 `ranking` 配置保持；无配置的新用户走向导，默认中立。
4. **custom-routes**：当前用户的 `x-opencode-free` 声明保留为"该用户配置"，包模板里改成空 `routes: []` + 注释示例。
5. **回滚**：每一步都可逆——恢复文件即回旧行为；不改生产配置的本轮不动任何真实文件。
