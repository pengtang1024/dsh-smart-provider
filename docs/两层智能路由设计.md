# 两层智能路由设计（定位驱动 · 可编码级）

> 状态：只读设计稿（task-55），深化《落地规格.md》P2，不推翻前五份设计。**不改任何代码/配置/插件，不重启 DSH**。
> 用户纠正落点：**「复合=智能——先按任务性质/模型定位选档，再档内成本/速度加权，不是六因素线性求和」**。
> 结论先行：**第一层按"任务性质 × 模型定位"选候选档（离散、可解释），第二层在候选档内用现有 `ranking.js` 四因素加权（连续、可微调）。未配置时两层都是直通（identity），行为逐字节等于现状——已验证的省钱链路（x-opencode-free 免费首跳、402→付费 fallback）不受影响。**

## 0. 设计总览（工程师一页读懂）

```
GenerateOptions（不改接口）
  → ① 任务识别 classifyTask(options) → TaskKind + 置信信号
  → ② 档位选择 selectTiers(task, positions, config) → Tier[]（候选定位档，有序）
  → ③ hard filter：候选 route 的能力/上下文不足则剔除，空则放宽+WARN
  → ④ 档内择优：对每档的 accounts 用 rankAccountsForHop() 四因素打分排序
  → ⑤ 合成 attempts（按 Tier 顺序 → 档内 score 顺序）交给现有逐 hop 循环
```

两层的关键区别：**第一层是"离散选档"（哪些模型属于这个任务，二分+列出），第二层是"连续打分"（选中的这几个里谁先上）**。六因素线性求和（旧稿）被拆开：能力判定归第一层（hard filter），成本/速度/等级/负载归第二层（软加权）。

## 1. 模型定位（position）数据模型

### 1.1 定位标签集（7 个，产品定义，不照抄示例）

| 标签 id | 中文名 | 语义 | 自动可推导？ |
|---|---|---|---|
| `thrifty` | 省钱够用 | 价格低/免费，质量够用 | 部分（priceTier=free/low 或 price=0） |
| `swift` | 极速响应 | 低延迟、短输出优先 | 部分（speedTier=fast，**手填为主**） |
| `reasoning` | 深度推理 | 支持 thinking、强逻辑 | ✅（`Model.reasoning=true`） |
| `longctx` | 长上下文 | 大 contextWindow | ✅（`Model.contextWindow ≥ 阈值`） |
| `vision` | 多模态看图 | input 含 image | ✅（`Model.input` 含 `"image"`） |
| `tool` | 工具调用 | 能稳定发 tool-call | ❌ catalog 无字段，**手填/默认 chat=yes** |
| `general` | 全能均衡 | 兜底档，无明显偏向 | ✅（其它都不命中时的中性档） |

> 一个模型可持多个标签（如 reasoning+longctx+tool）。定位是**能力画像**，不是账号等级——与 `account.tier` 不同维度。

### 1.2 自动推导规则表（读 asar 确认字段）

历史依据（**已过时，仅保留为当时的推导出处**）：pi-ai `dist/types.d.ts:644-682` —— `BaseModel.input: ModelInputModality[]`(:653)、`Model.reasoning: boolean`(:667)、`Model.contextWindow: number`(:675)、`Model.maxTokens: number`(:676)。当前 DSH Host 的真实类型已是自家的 `LlmModelInfo` / `LlmResolvedModelInfo`：`reasoning` 是 `{efforts}` 对象而非布尔、`contextWindow` 在 `context.contextWindow`、模态字段叫 `inputModalities`；`session.modelCatalog()` 的 strict codec 经实测**只投影 `id/name/description/reasoning{efforts}/badge`**，没有 `contextWindow` / `input` / `tool`。下表规则保留原设计意图；逐台展示已改走 §1.2 末的 `@Remote modelPositions()` Host 投影。

| 标签 | 推导规则 | 数据源 | 拿不到时 |
|---|---|---|---|
| reasoning | `model.reasoning === true` | pi-ai catalog（自动） | 用户手填 `capabilities.reasoning` |
| longctx | `model.contextWindow >= 200000`（阈值可配） | pi-ai catalog（自动） | 手填 contextWindow |
| vision | `model.input.includes('image')` | pi-ai catalog（自动） | 手填；默认保守=no |
| tool | catalog 无字段 → chat 模型默认 yes，user 可覆盖 | 手填 | 默认 yes（避免误杀），逐台表展示时标「未确认」而非实测能力 |
| thrifty | `priceFor()==0` 或 `priceTier ∈ {free,low}` | 用户定价表/档位（见资源自适应设计） | 无定价时不自动打 thrifty（中立） |
| swift | `account.speedTier==='fast'` | 用户手填（ranking.js:82-93 已有字段） | 默认 normal，不打 swift |
| general | 以上都不命中 | 兜底 | — |

**数据通路已实测（一期已闭环，原「未验证」项已修正）**：旧的「`listModels()` 是否原样暴露 `reasoning/contextWindow/input`」疑问已有结论 —— **不成立**。Host `session/modelCatalog()` 的 strict codec 逐字段核对后只投影 `id/name/description/reasoning{efforts}/badge`，**没有 `contextWindow` / `input` / `inputModalities` / `tool`**，且 `reasoning` 是 efforts 对象而非布尔值（`resolveModelInfo()` 内部虽短暂持有 `context.contextWindow` 与 `inputModalities`，投影时被 Host 自己丢掉）。因此「前端拿 catalog 能力字段自算定位」已证伪；逐台真实定位表改走 Host 新增的 `@Remote modelPositions()`：由 Host 侧纯投影 `adapter.routes` + `resolveModelInfo` 能力 + `positionOverrides`，显式映射真实字段（`inputModalities→input`、`context.contextWindow→contextWindow`、`reasoning.efforts→reasoning` 代理）后调用 `derivePosition()`，返回 `{enabled, rows}`，每行 `{id, name, group, tags, source}`（wire tags 仅 `reasoning` / `multimodal` / `tool` / `longctx` / `general` 五种，内部 `vision` 投影为 `multimodal`）。读不到逐台数据时显示「未确认」空态、不展示猜测结果、**不伪造行**；`thrifty` / `swift` 永远不能自动推导。该投影只服务设置页只读展示，不改选路逻辑；「个别模型手填」仍走 `ranking.routing.positionOverrides` / `registry/position-overrides.user.yaml`，本期不新增 UI 控件。

### 1.3 定位与 account.tier/priceTier/speedTier 的关系（不冲突，分层）

- `position` 是**模型级能力画像**（这个模型能干什么），标签集见 §1.1。
- `account.tier/priceTier/speedTier` 是**账号级运营属性**（这个账号贵不贵、快不快、优先级），现有 ranking.js:178-205 已归一化。
- 归一规则：**同名不同义，禁止互相覆盖**。position 存在模型 catalog / 手填声明里；tier 等存在 account 配置里。评分时 position 只决定"进哪个档"，tier 等只在档内第二层起作用（tier→tier 因素、speedTier→speed 因素、priceTier→cost 代理）。

## 2. 任务性质识别（第一层输入）

### 2.1 证据：GenerateOptions 真实字段（不改接口）

`dsh-tauri/runtime/node_modules/@deepseek-ai/dsh-llm/src/types.ts:564` + `docs/subsystems/llm-streaming.zh.md:667-706` + `lib/typert.host.js:360` 三处一致：

```ts
interface GenerateOptions {
  provider: string; model: string;
  reasoningEffort?: ReasoningEffortId;   // 推理强度
  messages: RequestMessage[];            // 消息体（可含 image content）
  system?: string; tools?: ToolSchema[]; // 工具声明
  toolHistory?: ToolHistory; temperature?: number; maxTokens?: number;
  stop?: string[]; signal?: AbortSignal;
  sessionId?: Branded<'SessionId'>;
  purpose?: Purpose;                     // 辅助请求用途（compaction/session-title…）
}
```

全部为现有字段——**调用方无需改接口**，识别器只读不改。

### 2.2 识别规则（字段 → TaskKind）

| 信号（按优先级） | 条件 | 识别为 | 证据 |
|---|---|---|---|
| P0 显式声明 | 外层模型 id 后缀 `+<position>`（如 `smart/auto+vision`）或 options 上可选 `requiredCapabilities` | 指定档，最高优先 | 能力设计 §3.2 兜底口径 |
| P1 图片 | `messages` 任一 content.type=`'image'` | vision | pi-ai types.d.ts:490（图片需模型 input 含 image）；GenerateOptions.messages |
| P2 工具 | `options.tools?.length > 0` | tool | GenerateOptions.tools（:工具 schema） |
| P3 推理 | `options.reasoningEffort` 非 none/undefined | reasoning | GenerateOptions.reasoningEffort |
| P4 长文本 | 估算 messages token > 阈值（默认 200000，可配） | longctx | 估算方法见下 |
| P5 辅助用途 | `options.purpose` 命中已知轻量用途（session-title 等） | thrifty | GenerateOptions.purpose 是辅助调用分类 |
| P6 兜底 | 都不命中 | general | 中立默认 |

**token 估算**：无精确 tokenizer 时用字符数/4 粗估（务实口径，标未验证精度）；只用于"是否超长"的阈值判断，不用于计费。

### 2.3 多信号冲突优先级表

冲突时**取最高优先的一个主任务性质**，其余作为"次要标签"进入候选档集合（不丢弃，见 §3.1）：

| 冲突场景 | 裁决 | 理由 |
|---|---|---|
| image + tools（多模态工具调用） | 主=vision，次=tool | 图片是硬能力门槛，先满足 |
| reasoningEffort + 长文本 | 主=reasoning，次=longctx | 推理强度影响输出质量，优先保 |
| 显式 `+position` + 任何自动信号 | 主=显式 | 用户声明最高优先 |
| 全部命中 | 主=显式（若无则 P1 顺序），次=其余全部 | 多路并列候选，档内再排 |

## 3. 档位选择（第一层）

### 3.1 任务性质 → 候选定位集合（条件→档，可多路）

| TaskKind（主） | 候选档（有序） | hard filter 条件 | 空候选处理 |
|---|---|---|---|
| vision | [vision] | 模型 `input` 不含 image → 剔除 | 放宽：允许全部模型，按缺失维度最少排序 + WARN |
| tool | [tool] | 声明 `tool=false` 的模型剔除 | 默认 chat=yes，通常不空 |
| reasoning | [reasoning, general] | `reasoning=false` 剔除 | 放宽到 general + WARN |
| longctx | [longctx, general] | `contextWindow < 估算 token` 剔除 | 放宽到最大 contextWindow 的模型 + WARN |
| thrifty | [thrifty, general] | 无硬过滤（价格是软因素） | 不过滤 |
| general | [general] + 其它档按配置 | 无 | — |

- **hard filter 语义**：二元能力（vision/tool）不满足 → 直接剔除（发图片给无 vision 模型必然 400，打分再高无意义）；程度能力（reasoning 强度、context 余量）→ 进档内 soft score 或按阈值剔除。
- **空候选兜底**：不硬失败，放宽并重排 + 记 WARN（`logger.warn`），保证可用性优先；这是"能力不满足不阻断用户"的底线。

### 3.2 档选择是"路由器的第一跳"，不是重排全部账号

候选档是有序的小集合（通常 1–2 档）。第二层只对**当前档覆盖的账号/route**打分，不是把全部账号混排——这保证"任务性质决定能用什么模型"与"成本/速度决定先用谁"两层不互相污染。

## 4. 档内择优（第二层）

### 4.1 复用现有 ranking.js 四因素（不改公式）

`scoreAccounts()`（ranking.js:348-380）现有四因素 `cost / speed / tier / load` 与 `weight` 乘子、**priority hard 分层 + respectHopRoute + score DESC + tiebreak**（rankAccountsForHop:413-461）全部保留。

| 因素 | 档内是否保留 | 说明 |
|---|---|---|
| cost | ✅ | 档内谁便宜先用；priceTier 代理价仍有效（ranking.js:234-291） |
| speed | ✅ | speedTier→speedScore（ranking.js:311,321） |
| tier | ✅ | 账号等级（premium/standard/backup，ranking.js:312,326） |
| load | ✅ | 最少使用（account-pool.js:129 usage） |
| capability | ❌ 不进档内 | 已由第一层 hard filter / 档选择消费，不重复打分 |
| reliability | ❌ 不进档内 | 冷却机制（adapter.js:401-407）已表达可靠性，避免双重惩罚 |

> 旧稿《通用智能路由能力设计》§4.1 的"六因素统一加权"作废（落地规格 C2 裁决）；六因素拆为：能力→第一层，成本/速度/等级/负载→第二层，可靠性→现有冷却。

### 4.2 策略预设 → (档选择, 档内权重) 映射表

新增 two 参数：`tierPolicy`（第一层如何选档）与保留的 `strategy`（第二层档内权重）。**内置默认中立**（落地规格 C1：balanced 四因素等分 .25；cost-first .7 仅供选择，不是默认）。

| 预设 id | 中文名 | tierPolicy（第一层） | 档内 weights（第二层） |
|---|---|---|---|
| `balanced`（默认/中立） | 均衡 | auto（按任务识别候选档） | cost .25 / speed .25 / tier .25 / load .25 |
| `cost-first` | 省钱优先 | auto + 优先 thrifty 档 | cost .7 / speed .05 / tier .1 / load .15 |
| `speed-first` | 极速优先 | auto + 优先 swift 档 | cost .1 / speed .65 / tier .1 / load .15 |
| `reasoning-first` | 强推理 | 强制 reasoning 档 | cost .2 / speed .15 / tier .15 / load .15 + 档内 reasoning 强度 tiebreak |
| `longctx-first` | 长文档 | 强制 longctx 档 | cost .3 / speed .15 / tier .15 / load .2 + context 余量 tiebreak |
| `vision-first` | 看图 | 强制 vision 档 | cost .3 / speed .2 / tier .15 / load .2 |
| `legacy` | 兼容 | off（不使用两层） | 走现有比较器（route 优先+最少使用） |
| `custom` | 自定义 | 用户选 auto/强制档 | 用户填，归一化到和=1 |

- 映射实现：一个 `resolveRoutingPolicy(config)` 把预设解析为 `{tierPolicy, weights, positionOverrides}`，第二层仍调 `resolveWeights(strategy, weights)`（ranking.js:111）——**现有函数不改签名**。
- 用户新版 `strategy='balanced'` 默认走中立等分；当前用户旧 config 里的 cost 偏好作为其个人配置迁移保留（不进代码默认）。

### 5.3 向后兼容硬约束（逐字节边界）

1. **未配置 `ranking.routing`（或 `enabled:false`）**：`stream()` 的三个新调用点全部短路，`resolveChain`/`AccountPool.plan` 不传新参数 → 现有行为逐字节相等。已验证的省钱链路（cordis chains 免费首跳 x-opencode-free、402→cooldown→付费 hop、`usage.cost=0`）必须回归通过。
2. **已配 chains 的用户**：`resolveChain` 只在新参数存在时动态生成；老配置优先，不被两层覆盖。
3. **新因素不进旧公式**：`capability/reliability` 不入 `scoreAccounts` 的 contributions（ranking.js:370-377 不改），旧预设分数不变。
4. **position 缺失**：`derivePosition` 返回 `[general]`，不误杀、不报错。

## 6. 配置页呈现（小白 / 高级两层，首屏不假状态）

- **首屏（小白）**：只有一句中性陈述 + 三个大白话按钮："你想怎么用？省钱省电 / 反应要快 / 均衡就好"（对应 cost-first / speed-first / balanced）。**不显示任何"已启用/已优化/正在检测"字样**——用户已抓 4 次假状态；陈述只说"当前配置：X 模式"，来自 `configForms`（client.js:582 已验证通道），不读运行时猜状态。
- **高级区（折叠）**：定位标签、档选择规则、因素权重、任务识别阈值、catalog 推导覆盖——全部收进现有 `<details>`（client.js:181-190），小白默认看不到。
- **真实运行状态**（健康/冷却/实际走哪个档）：要么用可信来源（会话插件记录 `hop-selected`，adapter.js:233-253）显示，要么不显示；拿不到就诚实空态"暂无记录"，绝不停在转圈或假绿。
