# Intelligentes Modell-Routing (Smart Provider)

Ein als `smart` Route registrierter Meta-Provider. Er ruft selbst keine LLM-API auf — sondern versucht der Reihe nach deine **bereits konfigurierten DSH-Provider-Routen** und wählt die erste, die antwortet. Er ist ein **allgemeiner intelligenter Router**, kein Spar-Tool: die vier Ziele sind Kosten sparen / hohe Leistung / hohe Fähigkeiten / kombiniert (intelligent). Der Code ist standardmäßig neutral (ausgewogene Gewichtung .25), „Kosten zuerst" ist eine bewusste Konfigurationswahl des Nutzers.

**Aktueller Status: Plugin installiert und aktiviert, Plugin-Status ACTIVE.** Zwei Standard-Ebenen sind zu unterscheiden: **Innerhalb des Plugins ist das Standardmodell das virtuelle Modell „Intelligent“ (`smart`) mit der Standardintensität `auto`**; der **Host-Sitzungsstandard ist nun auf das virtuelle Modell „Intelligent“ gesetzt (umgesetzt)**: `agent-default-model` im Profil ist `provider: smart` / `model: smart` (einteilige Katalog-ID), die Intensität wird über die Einstellung `defaultEffort` bestimmt (Standard `auto`), und `smart/auto` ist nur eine interne Kombinations-ID, kein Wert für das Profil-Feld. Intelligentes Routing ist standardmäßig wirksam; Spar-Ketten, echte Lese-/Schreibzugriffe auf der Konfigurationsseite, P1 (Ressourcen-Adaption / neutrale Voreinstellung / dynamische Ketten) und P2 (zweistufiges intelligentes Routing, standardmäßig aktiv und neutral gewichtet, explizit abschaltbar) sind umgesetzt und separat abgenommen. Die Reihenfolge der Routen hängt von deiner aktuellen Registry und Konfiguration ab; dieses Dokument schreibt keine konkreten Zahlen fest.

## Funktionsmerkmale

- **Intelligentes Routing standardmäßig wirksam.** Innerhalb des Plugins ist das Standardmodell das virtuelle Modell „Intelligent“ (`smart`) mit der Standardintensität `auto` (Routenwahl und Fallback in echten Sitzungen verifiziert). Neuer Vertrag: **4 virtuelle Modelle** (Ausgewogen `balanced` / Sparsam `cost` / Effizient `speed` / Intelligent `smart`, standardmäßig Intelligent); **6 Intensitätsstufen** (`auto` + Aus `off` / Niedrig `low` / Mittel `medium` / Hoch `high` / Maximal `max`, standardmäßig `auto`). Der Katalog enthält nur 4 einteilige Modelle; die Intensität wird über die Einstellung `defaultEffort` separat gewählt; **24 Kombinations-IDs sind keine Katalogeinträge** (nur interne Analyse / Kompatibilität). `auto` ist eine **dynamische Neigung** aus Modell und Aufgabeninhalt, **keine feste Modell→Intensität-Zuordnung**; die intelligente Entscheidung von `classifyTask` bleibt erhalten, eine manuelle Wahl überschreibt auto. Alle vier Modellnamen und sechs Intensitätsnamen laufen über locale-Keys in 7 Sprachen `virtualModel.*` / `virtualEffort.*` (zh/en/de/es/fr/pt/ru); Chinesisch wird nicht mehr fest codiert. Die eingebaute Kettenliste ist bewusst leer; ohne Konfiguration erzeugt `discoverAutoChain()` aus der aktuellen DSH-Registry eine neutrale `smart`-Kette (sortiert nach Provider-/Modellname, ohne fest eingebaute Modelle bestimmter Nutzer).
- **Spar-Kette (vom Nutzer optional, nicht Standard).** Die kostenlose Route `x-opencode-free` (`hy4-flash-free`) wird durch `tier: free` in `registry/custom-routes.user.yaml` automatisch an den Anfang der Kette gesetzt; im echten Ledger kostet diese Route pro Eintrag `estimated_cost_usd=0` (213+ Einträge geprüft); bei 402-/Quota-Fehlern erfolgt der Fallback auf eine kostenpflichtige Route.
- **Account-Pool (mehrere Accounts = Pool).** Modell und Account sind zwei unabhängige Dimensionen. Jeder Hop der Kette bildet ein Modell auf einen Account-Pool ab (`{id, provider(Route), credentialRef, models[]}`); bevorzugt werden gesunde Accounts auf der Route dieses Hops, danach die am wenigsten genutzten; bevor zum nächsten Modell gewechselt wird, werden alle gesunden Accounts des aktuellen Modells versucht. Da DSH pro Route nur einen Key bindet, entspricht ein zweiter Account einer zweiten Provider-Route. Das `accounts`-Array ist optional; ohne Konfiguration ist das Verhalten byte-für-byte identisch mit der alten Version.
- **Account-Level-Cooldown.** Der Cooldown ist an `accountId` geknüpft, nicht an `provider/model`. Ein 402- oder Quota-Fehler bei einem Account friert nur diesen Account ein; andere Accounts desselben Modells bedienen weiterhin Anfragen.
- **Fallback nur vor dem Aufbau der Antwort.** Sobald ein Text-, Reasoning- oder Tool-Call-Block gesendet wurde, ist die Antwort festgelegt — bereits gesehene Tokens werden nicht zurückgenommen; `ABORTED` löst niemals einen Fallback aus.
- **Sitzungsprotokoll pro Versuch.** Jeder Versuch wird als ignorierbarer Plugin-Eintrag `plugin:dsh-smart-provider/hop-selected` mit der Nutzlast
  `{event:'smart/hop-selected', hopIndex, provider, model, accountId, failureCode, at}` geschrieben.
  Das ist der sichere, repo-externe Erweiterungsweg für `smart/hop-selected`: das direkte Senden eines unbekannten Ereignistyps würde dazu führen, dass die Sitzungspersistenz das Wiederherstellen des Logs verweigert.
- **Account-Ranking (P1, standardmäßig aktiv und neutral gewichtet, explizit abschaltbar).** Bewertung mit vier Faktoren: Kosten / Geschwindigkeit / Klasse / Last; `balanced` ist die neutrale Voreinstellung (.25), `cost-first` und ähnliche sind explizite Optionen; deaktiviert bleibt das alte Verhalten (Routenpriorität + am wenigsten genutzt).
- **Zweistufiges intelligentes Routing (P2, standardmäßig aktiv und neutral gewichtet, explizit abschaltbar).** `lib/routing.js` enthält vier reine Funktionen: Anfrageklassifizierung, Ableitung der Modell-Positionsmarken, Auswahl der Kandidaten-Ebene und Auflösung der Voreinstellungen. Standardmäßig aktiv (`ranking.routing.enabled=true`, `balanced`, vier gleich gewichtete Faktoren .25); mit `ranking.routing.enabled=false` läuft der Code byte-für-byte im Legacy-Modus. Acht Strategie-Voreinstellungen: `balanced` / `cost-first` / `speed-first` / `reasoning-first` / `longctx-first` / `vision-first` / `legacy` / `custom`. Positionsmarken werden automatisch aus dem Modell-Katalog abgeleitet (reasoning / contextWindow≥200000 / Eingabe enthält image / tool!==false / allgemein) und können mit `positionOverrides` manuell korrigiert werden; Konfigurationsfehler erzeugen nur eine WARN-Meldung und greifen auf Legacy zurück, ohne einen Absturz zu verursachen.
- **Schreibgeschützte Modellpositionierung auf der Konfigurationsseite (Phase 1).** Der zuvor unter „Routing → Account-Pool → Detaileinstellungen (standardmäßig eingeklappt) → zweistufiges Routing" versteckte schreibgeschützte Hinweis steht jetzt prominent auf der Konfigurationsseite: drei Sätze (dies ist eine schreibgeschützte Erklärung, keine editierbare Tabelle; die Position jedes Modells wird aus seinen eigenen Fähigkeiten abgeleitet; einzelne Modelle können zusätzlich manuell eingetragen werden) sowie die vier Regeln zur Aufgabenerkennung (**mit Bild → multimodale Stufe; Werkzeuge erforderlich → Werkzeug-Stufe; Reasoning erforderlich → Stufe für tiefes Denken; sehr langer Inhalt → Langtext-Stufe**). Neu ist eine **Tabelle mit echten Positionierungen pro Modell**: Sie liest über die neue `@Remote`-Methode `modelPositions()` eine reine Host-Projektion (`adapter.routes` + `resolveModelInfo`-Fähigkeiten + `positionOverrides`) und zeigt für jedes Modell Positionstags und Quelle (`auto` / `user` / `mixed`). **Die Fähigkeiten jedes Modells stammen aus der Host-Projektion**: der Strict-Codec von `session.modelCatalog()` projiziert nur `id/name/description/reasoning{efforts}/badge`, nicht aber `contextWindow` / `input` / `tool`; die Reasoning-Stufe wird über `reasoning.efforts` abgeleitet. Wenn die Daten pro Modell nicht gelesen werden können, zeigt die Tabelle den Status „unbestätigt" statt erfundener Zeilen. Statischer Hinweis und Tabelle sind schreibgeschützt; **es wird kein UI-Eingabefeld für manuelle Einträge hinzugefügt** — manuelle Korrekturen laufen weiter über `ranking.routing.positionOverrides` / `registry/position-overrides.user.yaml`.
- **Tab „Kosten / Gesundheit" mit echtem Ledger (die Konfigurationsseite hat seit 2.2.0 drei Tabs: Übersicht / Routing / Kosten & Gesundheit, zusammengeführt aus vier).** Die Kostenseite liest über die `@Remote`-Dienste `smartProvider.cost()` / `costDetail()` (`lib/remote.js`) die Aggregation von `lib/cost-stats.js` über die echte `cost.jsonl` (Gesamtkosten / kostenlos / kostenpflichtig / fehlgeschlagen / nach Provider) — keine Schätzungs-Platzhalter; die Detailtabelle trägt die sechs Latenzfelder plus ttft- / tok-s-Spalten, der Kostentrend wird nach **lokalem Kalendertag** gruppiert, und die Konfigurationsseite zeigt außerdem echte Provider-/Modelle und Credential-Namen aus pi-ai an.

- **Das native Intensitätssteuerelement im Dialog wird jetzt angezeigt (Stand 2026-11-28).** `lib/tier-ids.js::virtualReasoningDeclaration()` deklariert sechs `reasoning.efforts`-Stufen (`auto` + Aus `off` / Niedrig `low` / Mittel `medium` / Hoch `high` / Maximal `max`, Standard `auto`); `lib/adapter.js` ergänzt das Feld `reasoning` in `listModels`/`resolveModel` für smart-Einträge. Damit ist die Host-Bedingung `reasoning !== undefined` in `ModelSelect.tsx:498` erfüllt und die native Effort-Zeile erscheint — Nutzer können die Stufe wie bei anderen Modellen am gewohnten Ort wählen. `auto` schließt `off` ein: die Standardstufe lässt den Parameter weg und entscheidet dynamisch nach Modell und Aufgabe; eine manuell gewählte, vom ersten Hop nicht unterstützte Stufe (der kostenlose Hop unterstützt nur `off`) wird auf die zulässige Stufe `off` zurückgestuft, statt eine hohe Stufe zu senden. Die nativen Effort-Namen unterliegen dem Host-Codec (`z.string()`): Chinesisch in der zh-Oberfläche, sonst englischer Fallback; die 7-Sprach-Keys `virtualEffort.*` auf der Konfigurationsseite bleiben unverändert. Die frühere Aussage, das native Steuerelement bleibe verborgen und die Stufe werde nur auf der Konfigurationsseite festgelegt, ist hinfällig; Routing-Kette und erster Hop bleiben unverändert. Siehe `SPEC-2026-11-27-smart-provider.md` §7.1.

## Konfiguration

`chains`, `accounts`, `ranking` und `ranking.routing` sind volatile Konfigurationen; Änderungen auf der Konfigurationsseite gelten sofort, ohne Neustart. Die routing-Konfiguration ist unter `ranking.routing` verschachtelt (schema.js:62-67), Felder: `enabled` / `strategy` / `tierPolicy` / `weights` / `positionOverrides` / `tierLimit` / `longContextTokens` / `dynamicAuto`. Ohne Konfiguration wird dieser Codepfad überhaupt nicht ausgeführt; ein expliziter `chains`-Schlüssel und `*` haben immer Vorrang vor `dynamicAuto`, sodass alte Konfigurationen nicht überraschend verändert werden. Jeder Eintrag des Account-Pools `accounts` hat die Form `{id, provider, credentialRef, models[]}`; wenn er fehlt, läuft das alte per-Hop-Verfahren. Eigene Routen werden nur in `registry/custom-routes.user.yaml` deklariert (`credentialRef` enthält ausschließlich einen Referenznamen, niemals einen Klartext-Key).

Die detaillierte Begründung findet sich in drei Dokumenten des übergeordneten Arbeitsbereichs: `meta-provider-设计方案.md`, `多账号池设计方案.md`, `方案盲点审查.md`.

## Zusammenfassung (sekundär)

Ein als `smart` Route registrierter Meta-Provider, derzeit **installiert und aktiviert**; der Plugin-interne Standard ist das virtuelle Modell „Intelligent“ (`smart`) mit Intensität `auto`, während der Host-Sitzungsstandard jetzt auf das virtuelle Modell „Intelligent“ gesetzt ist (`agent-default-model` = `provider: smart` / `model: smart`, einteilige Katalog-ID; Intensität über `defaultEffort`, Standard `auto`; `smart/auto` ist nur eine interne Kombinations-ID, kein Profil-Wert). Er ist ein allgemeiner intelligenter Router (Kosten / Geschwindigkeit / Fähigkeiten / kombiniert), im Code neutral nach Voreinstellung; „Kosten zuerst" ist eine vom Nutzer aktivierte Konfiguration. Verifiziert: das virtuelle Modell „Intelligent“ (`smart`) mit `auto`-Intensität in echten Sitzungen (4 virtuelle Modelle, 6 Intensitätsstufen, 4 einteilige Katalogeinträge plus `defaultEffort`-Einstellung; `auto` ist eine dynamische Neigung, keine feste Zuordnung; Namen über locale-Keys in 7 Sprachen), kostenloser erster Hop `x-opencode-free` (cost=0, 213+ echte Ledger-Zeilen) mit Fallback 402→kostenpflichtig, eine Konfigurationsseite mit echten pi-ai-Ressourcen, einem `@Remote`-Ledger-Tab für Kosten und einer schreibgeschützten Modellpositionierungsansicht (statische Vier-Regel-Erkennung plus Tabelle echter Positionen pro Modell aus der neuen Host-Projektion `@Remote modelPositions()`, nicht lesbare Daten als „unbestätigt" angezeigt, manuelle Korrekturen weiterhin über Konfigurationsdateien), P1-Ressourcen-Adaption sowie standardmäßig aktives zweistufiges Routing (P2, `ranking.routing.enabled=true`, 8 Voreinstellungen, byte-für-byte Legacy bei Deaktivierung). Die vollständige Konfiguration und die Verifizierungsbefehle stehen in der README des Pakets.
