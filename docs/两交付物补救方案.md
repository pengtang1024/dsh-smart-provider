# 两交付物补救方案（task-31）

> 注：本文档写于 2.2.0 之前，设置页 Tab 结构与行号为旧状态；现行实现见 README §一 与 DETAIL.md

> 结论先行：**"提供商可见"与"专属配置页"两件事，一次改造就能一起完成，且不需要碰 Bifrost、不需要动池化算法、不需要改生产配置。**
>
> 核心判断（本轮只读源码实测，非猜测）：
> 1. **DUPLICATE_ADAPTER 是个伪矛盾**。`registerAdapter()` 与 `llm-pi-ai.providers` 走的是**两张不同的注册表**：前者写 `this.adapters`（dsh-llm/src/index.ts:416-474、:458），后者经 `registerConfigurableProviders()` 写 `this.directory`（:510-563）。真正会撞 DUPLICATE_ADAPTER 的只有**同名 route 被两个 adapter 各注册一次**——即"既让 pi-ai 注册 smart route、又让 SmartAdapter 注册 smart route"。本方案的确定做法是：**保留 registerAdapter(['smart'], SmartAdapter) 作为唯一注册源**，不动 pi-ai 的 providers 块。DUPLICATE_ADAPTER 从源头就不会发生。
> 2. **设置-模型页的数据源不是白名单**。`@deepseek-ai/dsh-client-ui-settings-models/src/client/store.ts:232-252` 把 `ctx.remote.llm.listProviders()`（=所有 `registerAdapter` 的 route，dsh-llm/src/index.ts:498-500）与 `listConfigurableProviders()` join。所以 **smart 只要注册成功，就会出现在一行里（displayName "Smart Gateway"）**。
> 3. **但 smart 现在根本没注册成功**。18:13 重启日志铁证：`cannot get property "llm" without inject`（dsh-smart-provider/index.js:21），全机 274 插件唯一 failed 项。这就是"设置页看不到 smart"的真正原因，跟 pi-ai provider 白名单无关。
> 4. 所以交付物的确定方案是：**Step 0 修 inject 让插件活过来（设置页自动出现 smart 行）→ 交付物2 用 settings.section 做专属配置页，顺带把 chains/accounts/ranking 都做成可视化编辑**。

## 1. 交付物 1：smart 成为设置-模型页可见、可配置的"提供商"

### 1.1 确定方案（唯一方案，不再讨论 A/B/C）

**保留 `registerAdapter(['smart'], SmartAdapter)`，不往 `llm-pi-ai.providers` 加 smart 块；只修 inject 让插件真正激活。**

- 为什么不是"改成 pi-ai provider route"：pi-ai 的 route 由 `dsh-llm-pi-ai/src/index.ts:332` 用**它自己的** `PiAiAdapter` 注册。若把 smart 也声明成 pi-ai route，pi-ai 会先注册 smart → SmartAdapter 再注册同名 route → `prepareRoutes()` 的 `DUPLICATE_ADAPTER`（dsh-llm/src/index.ts:458）必炸。要把调度逻辑换成 `llm/stream` waterfall 重写，等于把 390 行已验证的 SmartAdapter 推倒，代价和回归风险都不可接受。**没有收益。**
- 为什么"可见"不需要 pi-ai route：`listProviders()` 返回所有 adapter route，注册成功即出现。设置页 join 后显示为 active 行、模型选择器可列 smart/auto。**之前"不可见"纯粹是插件没活，不是设计缺失。**
- 让 smart 真正"可编辑"：设置页的编辑按钮由 `state.namespaces.has(row.entry.settingsNs)` 控制（`ModelsSection.tsx:369,428`）。smart 的 directory entry 没有 settingsNs（走 registerAdapter 而非 registerConfigurableProviders），因此行会出现但**没有原生"编辑"按钮**。这是可接受的——配置在专属配置页做，正好符合用户的第二个交付物。若将来想让 Models 页那行也有"编辑"，只需在 smart 插件 `apply()` 里追加一次 `ctx.llm.registerConfigurableProviders([{ provider:'smart', displayName:'Smart Gateway', settingsNs:'smart-provider', settingsPath:[] }])`（写的 directory 表、与 adapters 表互不冲突），并在客户端注册 `settings.models.provider-card` 扩展位塞一个"去配置"按钮跳到专属配置页。本轮不做，留作可选增强。

### 1.2 必做改动（Step 0，前置）

- `dsh-smart-provider/index.js` 顶部新增：
  ```js
  export const inject = ['llm', 'sessions']
  ```
  （若 cordis 拒绝 `sessions` 这个服务名，退一步只写 `['llm']` 并在 `apply` 内用 `ctx.inject(['sessions'], child => ...)`；以运行时报错为准，二选一即可。）
- 重启应用后确认日志不再有 `cannot get property ... without inject`、`plugin.state` 不再是 3=failed。

2. 设置 → 模型页：截图确认出现 **Smart Gateway** 一行（active）。
3. 模型选择器 `/model`：能看到 `Smart Auto (智能切换)` 及 `smart/deepseek-v4.1-flash` 等链模型。
4. 运行时断言（只读）：在能访问 `ctx.llm` 的地方 `listProviders()` 含 `{id:'smart',name:'Smart Gateway'}`；`listModels('smart')` 返回 ≥1 条。
5. 注意：`buildModelCatalog` 会对每个 provider 调 `resolveModelInfo`（:530）。SmartAdapter 的 `resolveModel` 委托首跳（adapter.js:182-189），需实测 smart 落在 `groups` 而非 `failures`；若落在 failures，补 `resolveModelInfo` 的委托实现（约 5 行）。

## 2. 交付物 2：专属配置页面（"Smart  provider"设置分区）

### 2.1 技术方案（确定）

复用 DSH 原生 `settings.section` slot 机制（与 Models/Plugins 页同款），新增一个客户端插件模块，以本地 bundle 形式挂在现有 `@local/dsh-smart-provider` 包上（**不新增第二个 bundle 行**）。

- 扩展点：`ctx.slots.inject('settings.section', () => ctx.slots.register({ name:'settings.section', id:'smart-provider', order:20, label:()=>t('nav'), inject: injected }, SmartSettingsSection))`
  - 范式来源：`dsh-client-ui-settings-models/src/client/index.ts:136-141`、`dsh-client-ui-settings-plugins/index.ts:76-79`。
  - 图标：`ctx.slots.inject('settings.section.icon', ...)` 注册同 `id` 图标（可选，README:47）。
- 客户端 manifest：在 `package.json` 的 `dsh` 下加 `"client": { "platform":"web", "immediately":true, "inject":["@deepseek-ai/dsh-client-ui-settings","@deepseek-ai/dsh-client-locale","@deepseek-ai/dsh-api-remotes"] }`；导出 `"./client":"./client.js"`；新增 `client.js` 为 `window.__ModuleLoader__.load({ id:'@local/dsh-smart-provider', factory(require){...} })` 格式（模板见 dsh-doc skill `templates/decoration/client.js`）。React 从 `require('react')` 拿，不引入第二份 React。
- 数据持久化（**关键约束**）：`dsh-settings` 只把 `.volatile()` 字段暴露给表单（`src/index.ts:386-389`）。因此：
  - **chains / accounts / ranking** 三个大对象字段在 `schema.js` 里从 `z.any().default(undefined)` 改为 `z.any().default(undefined).volatile()`（加 `.volatile()` 即可，仍是 JSON 对象，无类型变化）。
  - 客户端用 `ctx.configForms.get('smart-provider')` 拿到该 entry 的快照（`value/base/user/revision/writable`），写入走 `form.mutate([...ops], expectedRevision)`（ui-settings README:34）。这是官方支持的配置页路径，写入落在 profile patch 的 smart-provider 行，**不直接碰 cordis.patch.yml**。
  - 三个字段都是 volatile ⇒ 改完**无需重启**，Host 侧通过 `loader/volatile-update` 事件热更新（pi-ai 也用这个机制，见 dsh-llm-pi-ai/src/index.ts:340-346）。SmartAdapter 侧在 apply 里订阅该事件重建 chains/accounts/ranking（约 15 行）。
  - credentials 不进表单：账号的 `credentialRef` 只存引用名，密钥仍由 `credentials.set` 写（configuration.md:11）。
- 动态数据（健康/冷却、成本、评分解释）走第八节给的 Host 命令：`ctx.remote.commands.execute(name, input)`（已确认 `remote.commands` 在 dsh-api-remotes 挂载，:8/:200；签名为 `(command, input?, attachments?)`）。Host 侧 `index.js` 用 `ctx.commands.register()` 注册三个只读命令（dsh-commands README:32-35），命令实现直接读 adapter 内存状态 + cost.jsonl，返回 JSON 文本。UI 解析 JSON 渲染。这样避免新开 Remote namespace（Remote 是构建期固定集合，本地 bundle 加不进去）。

### 2.2 配置页结构（四个 Tab）

| Tab | 内容 | 读写方式 |
|---|---|---|
| **总览** | smart 启用状态、当前链路数、账号数、28 天成本小计、健康账号/冷却中账号；一键刷新 | `configForms.get('smart-provider')` 只读 + `commands.execute('smart.status')` |
| **切换链** | chains 的树形编辑：外层模型 → hop 列表（provider/model），增删改、拖动排序；默认链 `*` 的编辑 | `form.mutate(['chains' 路径 op])`，volatile 热更新 |
| **账号池 + 分级择优** | 账号表格 + 编辑弹窗；分级与多因素择优区（见 2.3） | `form.mutate(['accounts' / 'ranking' 路径 op])` |
| **成本 / 健康** | 按模型/实际 provider/账号聚合的花费表格（query-cost 同源）、近 7 天趋势、冷却中的账号及原因/剩余秒数 | `commands.execute('smart.cost')` / `commands.execute('smart.health')` |

### 2.3 账号池分级择优配置区（对接 account-ranking 的接口契约）

account-ranking agent 会在 `lib/ranking.js` 定义以下纯 JSON 元数据，配置页**直接消费，不另造字段**（详见 `账号池择优设计.md`）：

- `RANKING_STRATEGIES` → 策略预设下拉：`legacy | balanced | cost-first | speed-first | tier-first | custom`，每项显示 `label/description`。
- `RANKING_CONFIG_SCHEMA` → 自动渲染权重滑块的字段描述（id/type/enum/default/min/max/help）：`enabled`、`strategy`、`weights.{cost,speed,tier,load}`、`tierDirection`、`respectHopRoute`、`priorityMode`、`costInputWeight`。
- `ACCOUNT_RANKING_FIELDS` → 账号编辑弹窗里新增字段：`tier`（premium/standard/backup 或 3/2/1）、`priority`（数字越小越优先，**UI 必须提示与 tier 方向相反**）、`speedTier`（fast/normal/slow）、`priceTier`（free/low/mid/high）、`priceMultiplier`、`priceOverrides`、`weight`。
- `explainScore(account, model, config, ctx)` → "为什么选它"面板：展示 score、factors、contributions、why[]。
- `resolveEffectivePrice(...)` → 账号表格的"估算单价"列，并标注 source（override/table/tier-proxy/neutral）。
- **文案边界**：速率本期只有手动 `speedTier`；自动延迟统计明确标注 `future`（cost.jsonl 无起止时间，算不出延迟）；等级纯手填。不要写成"自动测速"。

### 2.4 Host 侧命令（只读，无需新 Remote）

在 `index.js` 内注册（示意，非最终代码）：

```js
ctx.effect(() => {
  const off = [
    ctx.commands.register({ name:'smart.status', description:'Smart provider status',
      handler: () => ({ kind:'text', text: JSON.stringify({
        registered: true, chains: Object.keys(adapter.chains), accounts: adapter.accountPool.size,
        cooldowns: [...adapter.cooldowns], revision: formRevision,
      }) }) }),
    ctx.commands.register({ name:'smart.cost', ... }),
    ctx.commands.register({ name:'smart.health', ... }),
  ]
  return () => off.forEach(d => d())
}, 'smart.commands')
```

命令返回的 JSON 文本由 UI `JSON.parse`。三个命令都只读，不暴露密钥；`credentialRef` 只回显引用名（打码）。

## 6. 纪律与边界

- 本轮（task-31）**只读调研 + 设计**，未改动任何生产配置、未安装/启用 bundle、未改 `cordis.patch.yml` / credentials。
