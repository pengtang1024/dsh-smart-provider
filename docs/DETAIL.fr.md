# Routage intelligent des modèles (Smart Provider)

Un méta-fournisseur enregistré comme route `smart`. Il n'appelle lui-même aucune API de grand modèle — il essaie plutôt, dans l'ordre, parmi vos **routes de fournisseurs DSH déjà configurées** et sélectionne la première qui répond. C'est un **routeur intelligent général**, pas un outil d'économie : les quatre objectifs sont coût / performance / capacité / composite (intelligent), et le code est neutre par défaut (poids équilibré .25) ; « coût prioritaire » est un choix de configuration de l'utilisateur.

**État actuel : le plugin est installé et activé, avec le statut ACTIVE.** Deux niveaux de valeur par défaut : **dans le plugin, le modèle par défaut est le modèle virtuel « Intelligent » (`smart`) avec l'effort `auto`** ; le **modèle par défaut de la session hôte est désormais appliqué au modèle virtuel « Intelligent »** : `agent-default-model` dans le profil est `provider: smart` / `model: smart` (identifiant de catalogue à segment unique), l'effort est déterminé par le paramètre `defaultEffort` (par défaut `auto`) et `smart/auto` n'est qu'un identifiant combiné interne, pas la valeur à saisir dans le profil. Le routage intelligent est actif par défaut ; la chaîne d'économie, la page de paramètres en lecture/écriture réelle, P1 (adaptation aux ressources / neutre par défaut / chaînes dynamiques) et P2 (routage intelligent à deux niveaux, actif par défaut et neutre, désactivable explicitement) sont tous implémentés et vérifiés indépendamment. L'ordre de routage dépend de votre registre en direct et de votre configuration ; ce document ne fixe donc aucun chiffre précis.

## Fonctionnalités

- **Routage intelligent actif par défaut.** Dans le plugin, le modèle par défaut est le modèle virtuel « Intelligent » (`smart`) avec l'effort `auto` (sélection de route et repli vérifiés en sessions réelles). Nouveau contrat : **4 modèles virtuels** (Équilibré `balanced` / Économique `cost` / Efficace `speed` / Intelligent `smart`, Intelligent par défaut) ; **6 niveaux d'effort** (`auto` + Arrêt `off` / Faible `low` / Moyen `medium` / Élevé `high` / Maximal `max`, `auto` par défaut). Le catalogue ne contient que 4 modèles à segment unique ; l'effort se choisit séparément via le paramètre `defaultEffort` : les 24 combinaisons **ne sont pas** des entrées du catalogue (analyse interne / compatibilité historique seulement). `auto` applique une **tendance dynamique** selon le modèle et le contenu de la tâche, **pas une correspondance fixe modèle→effort** ; la décision intelligente de `classifyTask` est conservée et un choix manuel remplace auto. Les quatre noms de modèle et six noms d'effort passent par des clés locale en 7 langues `virtualModel.*` / `virtualEffort.*` (zh/en/de/es/fr/pt/ru) ; le chinois n'est plus codé en dur. La liste de chaînes intégrée est volontairement vide ; sans configuration, `discoverAutoChain()` génère une chaîne `smart` neutre à partir du registre DSH en direct (triée par nom de fournisseur / modèle, sans intégrer les modèles d'un utilisateur précis).
- **Chaîne d'économie (optionnelle, non par défaut).** La route gratuite `x-opencode-free` (`hy4-flash-free`) est automatiquement placée en tête de chaîne grâce à `tier: free` dans `registry/custom-routes.user.yaml` ; dans le registre réel, chaque opération sur cette route a `estimated_cost_usd=0` (213+ entrées vérifiées) ; en cas d'erreur 402/quota, elle bascule vers une route payante.
- **Groupe de comptes (plusieurs comptes = mutualisation).** Modèle et compte sont deux dimensions indépendantes. Le modèle de chaque saut est associé à un groupe de comptes (`{id, provider(route), credentialRef, models[]}`) ; les comptes sains de la route du saut courant sont privilégiés, puis triés par moindre utilisation ; chaque compte sain d'un modèle est essayé avant de passer au modèle suivant. DSH ne lie qu'une seule clé par route : un deuxième compte = une deuxième route de fournisseur. Le tableau `accounts` est facultatif ; sans configuration, le comportement est identique octet pour octet à l'ancienne version.
- **Temporisation au niveau du compte.** La temporisation est indexée par `accountId`, et non par `provider/model`. Lorsqu'un compte rencontre une erreur 402 ou de quota, seul ce compte est gelé ; les autres comptes du même modèle continuent à servir.
- **Repli uniquement avant l'établissement.** Dès qu'un fragment de texte, de raisonnement ou d'appel d'outil a été émis, la réponse est engagée — il n'y a pas de repli sur des jetons déjà visibles ; `ABORTED` ne bascule jamais.
- **Journaux de session par tentative.** Chaque tentative est écrite comme un enregistrement de plugin ignorable `plugin:dsh-smart-provider/hop-selected`, avec la charge utile `{event:'smart/hop-selected', hopIndex, provider, model, accountId, failureCode, at}`. C'est le mécanisme d'extension sûr hors dépôt pour `smart/hop-selected` : émettre directement un type d'événement inconnu ferait refuser à la persistance de session la restauration du journal.
- **Classement des comptes ranking (P1, actif par défaut et neutre, désactivable explicitement).** Notation à quatre facteurs : coût / vitesse / niveau / charge ; `balanced` est le neutre par défaut (.25), tandis que `cost-first` et similaires sont des options explicites ; une fois désactivé, l'ancien comportement est conservé (priorité de route + moindre utilisation).
- **Routage intelligent à deux niveaux (P2, actif par défaut et neutre, désactivable explicitement).** `lib/routing.js` fournit quatre fonctions pures : classification de la requête, dérivation des étiquettes de position du modèle, sélection des niveaux candidats et résolution des préréglages. Il est actif par défaut (`ranking.routing.enabled=true`, `balanced`, quatre facteurs équivalents .25) ; avec `ranking.routing.enabled=false`, il suit l'ancien chemin octet pour octet. 8 préréglages de stratégie : `balanced` / `cost-first` / `speed-first` / `reasoning-first` / `longctx-first` / `vision-first` / `legacy` / `custom`. Les étiquettes de position sont dérivées automatiquement du catalogue de modèles (reasoning / contextWindow≥200000 / entrée contenant image / tool!==false / general) et peuvent être corrigées manuellement avec `positionOverrides` ; une erreur de configuration émet seulement un WARN et revient à l'ancien mode, sans plantage.
- **Affichage en lecture seule du positionnement des modèles dans la page de paramètres (phase 1).** La note en lecture seule auparavant cachée sous « Routage → pool de comptes → paramètres détaillés (repliés par défaut) → routage intelligent à deux niveaux » est désormais affichée bien en évidence : trois phrases (ceci est une explication en lecture seule, pas un tableau modifiable ; la position de chaque modèle est déduite de ses propres capacités ; certains modèles peuvent être complétés manuellement) ainsi que les quatre règles de reconnaissance des tâches (**avec image → niveau multimodal ; nécessite des outils → niveau outils ; nécessite du raisonnement → niveau de réflexion approfondie ; contenu très long → niveau texte long**). Un nouveau **tableau des positionnements réels par modèle** lit, via la nouvelle méthode `@Remote` `modelPositions()`, une projection pure côté Host (`adapter.routes` + capacités de `resolveModelInfo` + `positionOverrides`) et affiche pour chaque modèle les étiquettes de position et leur source (`auto` / `user` / `mixed`). **Les capacités de chaque modèle proviennent de la projection Host** : le strict codec de `session.modelCatalog()` ne projette que `id/name/description/reasoning{efforts}/badge`, sans `contextWindow` / `input` / `tool`, et le niveau de raisonnement est déduit de `reasoning.efforts`; lorsque les données par modèle ne peuvent pas être lues, le tableau affiche l'état « non confirmé » plutôt que des lignes inventées. La note statique et le tableau sont tous deux en lecture seule ; **aucun champ de saisie manuelle n'est ajouté à l'interface** — les corrections manuelles continuent de passer par `ranking.routing.positionOverrides` / `registry/position-overrides.user.yaml`.
- **Onglet coût et santé avec données de compte réelles (la page de paramètres a trois onglets depuis 2.2.0 : vue d'ensemble / routage / coût et santé, fusionnés à partir de quatre).** La page de coût lit, via les services `@Remote` `smartProvider.cost()` / `costDetail()` (`lib/remote.js`), l'agrégation calculée par `lib/cost-stats.js` sur le `cost.jsonl` réel (dépense totale / gratuites / payantes / échecs / par fournisseur) — et non un simple marqueur estimé ; le tableau de détail porte les six champs de latence et les colonnes ttft / tok-s, la tendance des coûts est regroupée par **jour calendaire local**, et la page de paramètres affiche en outre les vrais noms de fournisseur / modèle et d'identifiant d'authentification de pi-ai.

- **Le contrôle natif d'intensité dans la conversation s'affiche désormais (version 2026-11-28).** `lib/tier-ids.js::virtualReasoningDeclaration()` déclare six niveaux de `reasoning.efforts` (`auto` + Arrêt `off` / Faible `low` / Moyen `medium` / Élevé `high` / Maximal `max`, `auto` par défaut) ; `lib/adapter.js` ajoute le champ `reasoning` aux entrées smart dans `listModels`/`resolveModel`, satisfaisant la condition de l'hôte `reasoning !== undefined` dans `ModelSelect.tsx:498` — la ligne Effort native apparaît et l'utilisateur peut choisir un niveau au même endroit que pour les autres modèles. `auto` englobe `off` : le niveau par défaut omet le paramètre et est décidé dynamiquement selon le modèle et la tâche ; un niveau manuel non pris en charge par le premier saut (le saut gratuit ne prend en charge que `off`) est rétrogradé vers le niveau valide `off`, plutôt que d'envoyer un niveau élevé non pris en charge. Les noms natifs des efforts sont soumis au codec de l'hôte (`z.string()`) : chinois dans l'interface zh, repli anglais ailleurs ; les clés en 7 langues `virtualEffort.*` de la page de paramètres restent inchangées. L'ancienne formulation selon laquelle le contrôle natif restait masqué et l'intensité n'était définie que dans la page de paramètres est obsolète ; ni la chaîne de routage ni le premier saut ne changent. Voir `SPEC-2026-11-27-smart-provider.md` §7.1.

## Configuration

`chains`, `accounts`, `ranking` et `ranking.routing` sont des configurations volatile ; les modifications sur la page de paramètres prennent effet immédiatement, sans redémarrage. La configuration de routing est imbriquée sous `ranking.routing` (schema.js:62-67), avec les champs : `enabled` / `strategy` / `tierPolicy` / `weights` / `positionOverrides` / `tierLimit` / `longContextTokens` / `dynamicAuto`. Sans configuration, le chemin de code ne s'exécute pas du tout ; une clé `chains` explicite et `*` priment toujours sur `dynamicAuto`, les anciennes configurations ne sont donc pas affectées. Chaque entrée du groupe `accounts` a la forme `{id, provider, credentialRef, models[]}` ; si elle est omise, l'ancien mode par saut s'applique. Les routes personnalisées ne sont déclarées que dans `registry/custom-routes.user.yaml` (`credentialRef` ne contient qu'un nom de référence, jamais une clé en clair).

La conception détaillée repose sur trois documents de l'espace de travail parent : `meta-provider-设计方案.md`, `多账号池设计方案.md`, `方案盲点审查.md`.

## Résumé (secondaire)

Un méta-fournisseur enregistré comme route `smart`, actuellement **installé et activé** ; le défaut interne au plugin est le modèle virtuel « Intelligent » (`smart`) avec l'effort `auto`, tandis que le modèle par défaut de la session hôte est désormais appliqué au modèle virtuel « Intelligent » (`agent-default-model` = `provider: smart` / `model: smart`, identifiant de catalogue à segment unique ; effort via `defaultEffort`, par défaut `auto` ; `smart/auto` n'est qu'un identifiant combiné interne, pas une valeur de profil). C'est un routeur intelligent général (coût / vitesse / capacité / composite), neutre par défaut dans le code ; « coût prioritaire » est une configuration optionnelle de l'utilisateur. Vérifié : le modèle virtuel « Intelligent » (`smart`) avec l'effort `auto` en sessions réelles (4 modèles virtuels, 6 niveaux d'effort, 4 entrées de catalogue à segment unique plus le paramètre `defaultEffort` ; `auto` est une tendance dynamique, pas une correspondance fixe ; noms via clés locale en 7 langues), premier saut gratuit `x-opencode-free` (coût=0, 213+ lignes réelles du registre) avec bascule 402→payant, une page de paramètres avec les ressources réelles de pi-ai, un onglet coût `@Remote` utilisant le registre réel et une vue de positionnement des modèles en lecture seule (note statique à quatre règles plus un tableau des positionnements réels par modèle issu de la nouvelle projection Host `@Remote modelPositions()`, données illisibles affichées « non confirmé » et corrections manuelles toujours par fichiers de configuration), P1 (adaptation aux ressources) et P2 de routage à deux niveaux actif par défaut (`ranking.routing.enabled=true`, 8 préréglages, ancien comportement octet pour octet quand désactivé).
