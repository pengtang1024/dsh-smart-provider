# Routage intelligent des modèles (Smart Provider)

Un méta-fournisseur enregistré comme route `smart`. Il n'appelle lui-même aucune API de grand modèle — il essaie plutôt, dans l'ordre, parmi vos **routes de fournisseurs DSH déjà configurées** et sélectionne la première qui répond. C'est un **routeur intelligent général**, pas un outil d'économie : les quatre objectifs sont coût / performance / capacité / composite (intelligent), et le code est neutre par défaut (poids équilibré .25) ; « coût prioritaire » est un choix de configuration de l'utilisateur.

**État actuel : le plugin est installé et activé, défini comme modèle par défaut, et son état est ACTIVE.** Le routage intelligent est actif par défaut ; la chaîne d'économie, la page de paramètres en lecture/écriture réelle, P1 (adaptation aux ressources / neutre par défaut / chaînes dynamiques) et P2 (routage intelligent à deux niveaux, actif par défaut et neutre, désactivable explicitement) sont tous implémentés et vérifiés indépendamment. L'ordre de routage dépend de votre registre en direct et de votre configuration ; ce document ne fixe donc aucun chiffre précis.

## Fonctionnalités

- **Routage intelligent actif par défaut.** `smart/auto` est le modèle par défaut ; la sélection de route et le repli ont été vérifiés dans des sessions réelles. La liste de chaînes intégrée est volontairement vide ; sans configuration, `discoverAutoChain()` génère une chaîne `auto` neutre à partir du registre DSH en direct (triée par nom de fournisseur / modèle, sans intégrer les modèles d'un utilisateur précis).
- **Chaîne d'économie (optionnelle, non par défaut).** La route gratuite `x-opencode-free` (`hy4-flash-free`) est automatiquement placée en tête de chaîne grâce à `tier: free` dans `registry/custom-routes.user.yaml` ; dans le registre réel, chaque opération sur cette route a `estimated_cost_usd=0` (213+ entrées vérifiées) ; en cas d'erreur 402/quota, elle bascule vers une route payante.
- **Groupe de comptes (plusieurs comptes = mutualisation).** Modèle et compte sont deux dimensions indépendantes. Le modèle de chaque saut est associé à un groupe de comptes (`{id, provider(route), credentialRef, models[]}`) ; les comptes sains de la route du saut courant sont privilégiés, puis triés par moindre utilisation ; chaque compte sain d'un modèle est essayé avant de passer au modèle suivant. DSH ne lie qu'une seule clé par route : un deuxième compte = une deuxième route de fournisseur. Le tableau `accounts` est facultatif ; sans configuration, le comportement est identique octet pour octet à l'ancienne version.
- **Temporisation au niveau du compte.** La temporisation est indexée par `accountId`, et non par `provider/model`. Lorsqu'un compte rencontre une erreur 402 ou de quota, seul ce compte est gelé ; les autres comptes du même modèle continuent à servir.
- **Repli uniquement avant l'établissement.** Dès qu'un fragment de texte, de raisonnement ou d'appel d'outil a été émis, la réponse est engagée — il n'y a pas de repli sur des jetons déjà visibles ; `ABORTED` ne bascule jamais.
- **Journaux de session par tentative.** Chaque tentative est écrite comme un enregistrement de plugin ignorable `plugin:dsh-smart-provider/hop-selected`, avec la charge utile `{event:'smart/hop-selected', hopIndex, provider, model, accountId, failureCode, at}`. C'est le mécanisme d'extension sûr hors dépôt pour `smart/hop-selected` : émettre directement un type d'événement inconnu ferait refuser à la persistance de session la restauration du journal.
- **Classement des comptes ranking (P1, actif par défaut et neutre, désactivable explicitement).** Notation à quatre facteurs : coût / vitesse / niveau / charge ; `balanced` est le neutre par défaut (.25), tandis que `cost-first` et similaires sont des options explicites ; une fois désactivé, l'ancien comportement est conservé (priorité de route + moindre utilisation).
- **Routage intelligent à deux niveaux (P2, actif par défaut et neutre, désactivable explicitement).** `lib/routing.js` fournit quatre fonctions pures : classification de la requête, dérivation des étiquettes de position du modèle, sélection des niveaux candidats et résolution des préréglages. Il est actif par défaut (`ranking.routing.enabled=true`, `balanced`, quatre facteurs équivalents .25) ; avec `ranking.routing.enabled=false`, il suit l'ancien chemin octet pour octet. 8 préréglages de stratégie : `balanced` / `cost-first` / `speed-first` / `reasoning-first` / `longctx-first` / `vision-first` / `legacy` / `custom`. Les étiquettes de position sont dérivées automatiquement du catalogue de modèles (reasoning / contextWindow≥200000 / entrée contenant image / tool!==false / general) et peuvent être corrigées manuellement avec `positionOverrides` ; une erreur de configuration émet seulement un WARN et revient à l'ancien mode, sans plantage.
- **Onglet coût et santé avec données de compte réelles (la page de paramètres a trois onglets depuis 2.2.0 : vue d'ensemble / routage / coût et santé, fusionnés à partir de quatre).** La page de coût lit, via les services `@Remote` `smartProvider.cost()` / `costDetail()` (`lib/remote.js`), l'agrégation calculée par `lib/cost-stats.js` sur le `cost.jsonl` réel (dépense totale / gratuites / payantes / échecs / par fournisseur) — et non un simple marqueur estimé ; le tableau de détail porte les six champs de latence et les colonnes ttft / tok-s, la tendance des coûts est regroupée par **jour calendaire local**, et la page de paramètres affiche en outre les vrais noms de fournisseur / modèle et d'identifiant d'authentification de pi-ai.

## Configuration

`chains`, `accounts`, `ranking` et `ranking.routing` sont des configurations volatile ; les modifications sur la page de paramètres prennent effet immédiatement, sans redémarrage. La configuration de routing est imbriquée sous `ranking.routing` (schema.js:62-67), avec les champs : `enabled` / `strategy` / `tierPolicy` / `weights` / `positionOverrides` / `tierLimit` / `longContextTokens` / `dynamicAuto`. Sans configuration, le chemin de code ne s'exécute pas du tout ; une clé `chains` explicite et `*` priment toujours sur `dynamicAuto`, les anciennes configurations ne sont donc pas affectées. Chaque entrée du groupe `accounts` a la forme `{id, provider, credentialRef, models[]}` ; si elle est omise, l'ancien mode par saut s'applique. Les routes personnalisées ne sont déclarées que dans `registry/custom-routes.user.yaml` (`credentialRef` ne contient qu'un nom de référence, jamais une clé en clair).

La conception détaillée repose sur trois documents de l'espace de travail parent : `meta-provider-设计方案.md`, `多账号池设计方案.md`, `方案盲点审查.md`.
