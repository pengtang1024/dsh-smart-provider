# Roteamento inteligente de modelos (Smart Provider)

Um meta-provedor registrado como a rota `smart`. Ele não chama nenhuma API de modelo diretamente — em vez disso, tenta em sequência as **rotas de provedores DSH que você já configurou** e escolhe a primeira que responde. É um **roteador inteligente geral**, não uma ferramenta de economia: os quatro objetivos são economia / alto desempenho / alta capacidade / composto (inteligente). O código é neutro por padrão (ponderação equilibrada .25); «priorizar custo» é uma escolha explícita de configuração do usuário.

**Estado medido no ambiente de desenvolvimento deste projeto (não uma afirmação universal): plugin instalado e habilitado, status ACTIVE, e a sessão do host persistiu o modelo virtual «Inteligente»; novos usuários devem verificar seu próprio perfil.** Duas camadas de padrão: **dentro do plugin, o modelo padrão é o modelo virtual «Inteligente» (`smart`) com intensidade `auto`**; neste ambiente de desenvolvimento a **sessão do host persistiu o modelo virtual «Inteligente»**: `agent-default-model` no perfil é `provider: smart` / `model: smart` (id de catálogo de segmento único), a intensidade é determinada pela configuração `defaultEffort` (padrão `auto`) e `smart/auto` é apenas um id combinado interno, não o valor preenchido no perfil. O roteamento inteligente está ativo por padrão; cadeias de economia, leitura e escrita reais na página de configuração, P1 (adaptação a recursos / padrão neutro / cadeias dinâmicas) e P2 (roteamento inteligente de duas camadas, ativo por padrão e neutro, desativável explicitamente) foram implementados e validados de forma independente. A ordem das rotas depende do seu registro em tempo real e da configuração; este documento não fixa números específicos.

## Recursos

- **Roteamento inteligente ativo por padrão.** Dentro do plugin, o modelo padrão é o modelo virtual «Inteligente» (`smart`) com intensidade `auto` (seleção de rota e fallback validados em sessões reais). Novo contrato: **4 modelos virtuais** (Equilibrado `balanced` / Econômico `cost` / Eficiente `speed` / Inteligente `smart`, Inteligente por padrão); **6 níveis de intensidade** (`auto` + Desligado `off` / Baixo `low` / Médio `medium` / Alto `high` / Máximo `max`, `auto` por padrão). O catálogo lista apenas 4 modelos de segmento único; a intensidade é escolhida separadamente pela configuração `defaultEffort`; as 24 combinações **não** são entradas do catálogo (apenas análise interna / compatibilidade histórica). `auto` aplica uma **inclinação dinâmica** conforme modelo e conteúdo da tarefa, **não um mapeamento fixo modelo→intensidade**; a decisão inteligente de `classifyTask` é preservada e uma escolha manual substitui o auto. Os quatro nomes de modelo e seis de intensidade usam chaves locale em 7 idiomas `virtualModel.*` / `virtualEffort.*` (zh/en/de/es/fr/pt/ru); chinês não é mais codificado. A lista de cadeias embutida é deliberadamente vazia; sem configuração, `discoverAutoChain()` gera a partir do registro DSH em tempo real uma cadeia `smart` neutra (ordenada por nome de provedor/modelo, sem modelos específicos de determinados usuários embutidos).
- **Cadeia de economia (opcional, não padrão).** A rota gratuita `x-opencode-free` (`hy4-flash-free`) é automaticamente colocada no início da cadeia por `tier: free` em `registry/custom-routes.user.yaml`; no ledger real, cada entrada dessa rota tem `estimated_cost_usd=0` (213+ entradas verificadas); em caso de erro 402/cota, há fallback para uma rota paga.
- **Pool de contas (várias contas = pool).** Modelo e conta são duas dimensões independentes. Cada salto da cadeia mapeia um modelo para um pool de contas (`{id, provider(rota), credentialRef, models[]}`); são preferidas contas saudáveis na rota daquele salto e, em seguida, as menos utilizadas; antes de passar para o próximo modelo, todas as contas saudáveis do modelo atual são tentadas. Como o DSH associa apenas uma chave a cada rota, uma segunda conta corresponde a uma segunda rota de provedor. O array `accounts` é opcional; sem configuração, o comportamento é byte a byte idêntico ao da versão antiga.
- **Resfriamento por conta.** O resfriamento é indexado por `accountId`, não por `provider/model`. Um erro 402 ou de cota em uma conta congela apenas aquela conta; outras contas do mesmo modelo continuam atendendo.
- **Gestão automática de saúde em três camadas (ativa por padrão).** As camadas de modelo, conta e topologia mantêm registros separados em um mesmo registro compartilhado; 4xx por forma da requisição ou cabeçalho ausente nunca afeta a saúde do modelo; uma conta em resfriamento só volta de `HALF_OPEN` para `ACTIVE` após uma requisição real bem-sucedida; rotas com pool de contas próprio não são embrulhadas de novo (apenas evidência estrutural, sem listas de nomes de provedores). Uma sonda real de 1 token substitui adivinhações de «gratuito/pago» pelo nome; `unknown` nunca bloqueia. A hidratação na partida a frio (1.2.0) reproduz `cost.jsonl` e `probe-cache.jsonl` nos mesmos registros L1/L2 (somente leitura, limites de 4 MiB / 5000 linhas, nunca sobrescrevendo evidência ao vivo mais recente). A desativação explícita (`health: false` / `health.enabled: false` / `ranking.health.enabled: false`) volta byte a byte ao modo legacy e nem abre os arquivos.
- **Medição de latência em `cost.jsonl`.** Cada linha de custo pode conter `started_at` / `first_token_at` / `finished_at` (marcas ISO), `ttft_ms`, `duration_ms` e `tokens_per_second`; linhas sem essas chaves são simplesmente omitidas e a agregação de linhas antigas não muda. O ranking e a página de custos consomem essas métricas derivadas.
- **Relatório de consulta (`scripts/query-cost.mjs`, duas seções acrescentadas desde 1.2.0).** O resumo de gastos e a tabela por grupo permanecem inalterados; depois vêm **failure rate** (`failed / calls` por grupo; apenas linhas com `failure_code` real contam como falhas) e **latency** (média de `ttft`, `p50` nearest-rank, número de amostras ttft, média de `tok/s`, número de amostras tps). Linhas antigas sem chaves de latência são excluídas — nunca contadas como 0 ms; um `ttft_ms=0` real continua sendo amostra válida; <3 amostras recebem `*`, sem amostra `-`, e uma execução sem amostras mostra um estado vazio honesto; valores inválidos nunca geram `NaN`.
- **Preços são dados do usuário.** O `lib/pricing.json` incluído contém apenas declarações de gratuidade a preço zero (4 linhas); preços reais são importados por `DSH_SMART_PRICING_FILE` ou `registry/pricing.user.json` (variável de ambiente → tabela do usuário → tabela padrão). Modelos sem linha de preço recebem uma estimativa por nível (`known:false` / `estimated:true`, valor sempre 0); a exportação de preços reais do autor permanece como exemplo em `lib/pricing.example.json`, fora do caminho padrão de carregamento.
- **Fallback apenas antes do estabelecimento da resposta.** Assim que qualquer bloco de texto, raciocínio ou chamada de ferramenta é enviado, a resposta está confirmada — os tokens já mostrados não são retirados; `ABORTED` nunca dispara fallback.
- **Registro de sessão por tentativa.** Cada tentativa é gravada como uma entrada de plugin ignorável `plugin:dsh-smart-provider/hop-selected`, com o payload
  `{event:'smart/hop-selected', hopIndex, provider, model, accountId, failureCode, at}`.
  Essa é a forma segura de extensão fora do repositório para `smart/hop-selected`: enviar diretamente um tipo de evento desconhecido faria com que a persistência de sessão se recusasse a restaurar o log.
- **Classificação de contas (P1, ativa por padrão e neutra, desativável explicitamente).** Pontuação por quatro fatores: custo / velocidade / nível / carga; `balanced` é o padrão neutro (.25), `cost-first` e semelhantes são opções explícitas; desativada, mantém o comportamento antigo (prioridade de rota + menos usada).
- **Roteamento inteligente de duas camadas (P2, ativo por padrão e neutro, desativável explicitamente).** `lib/routing.js` contém quatro funções puras: classificação da requisição, derivação das etiquetas de posição do modelo, seleção da camada de candidatos e resolução de predefinições. Ativo por padrão (`ranking.routing.enabled=true`, `balanced`, quatro fatores iguais .25); com `ranking.routing.enabled=false`, o código segue byte a byte no modo legacy. Oito predefinições de estratégia: `balanced` / `cost-first` / `speed-first` / `reasoning-first` / `longctx-first` / `vision-first` / `legacy` / `custom`. As etiquetas de posição são derivadas automaticamente do catálogo de modelos (reasoning / contextWindow≥200000 / entrada contém image / tool!==false / geral) e podem ser corrigidas manualmente com `positionOverrides`; erros de configuração apenas geram um WARN e revertem para legacy, sem causar falha.
- **Exibição somente leitura da posição dos modelos na página de configurações (fase 1).** A nota somente leitura antes escondida em «Roteamento → pool de contas → configurações detalhadas (recolhidas por padrão) → roteamento inteligente de duas camadas» agora aparece em local visível: três frases (isto é uma explicação somente leitura, não uma tabela editável; a posição de cada modelo é derivada de suas próprias capacidades; modelos individuais podem ser preenchidos manualmente) mais as quatro regras de reconhecimento de tarefas (**com imagem → nível multimodal; precisa de ferramentas → nível de ferramentas; precisa de raciocínio → nível de pensamento profundo; conteúdo muito longo → nível de texto longo**). Acrescenta-se ainda uma **tabela com as posições reais por modelo**, que lê pelo novo método `@Remote` `modelPositions()` uma projeção pura do Host (`adapter.routes` + capacidades de `resolveModelInfo` + `positionOverrides`) e mostra, para cada modelo, as etiquetas de posição e a origem (`auto` / `user` / `mixed`). **As capacidades de cada modelo vêm da projeção do Host**: o strict codec de `session.modelCatalog()` projeta apenas `id/name/description/reasoning{efforts}/badge`, sem `contextWindow` / `input` / `tool`, e o nível de raciocínio é inferido de `reasoning.efforts`; quando os dados por modelo não podem ser lidos, a tabela mostra o estado «não confirmado» em vez de inventar linhas. Tanto a nota estática quanto a tabela são somente leitura; **nenhum campo de preenchimento manual é adicionado à interface** — correções manuais continuam indo por `ranking.routing.positionOverrides` / `registry/position-overrides.user.yaml`.
- **Aba «Custo e saúde» com ledger real (a página de configuração tem três abas desde 2.2.0: visão geral / roteamento / custo e saúde, unificadas a partir de quatro).** A página de custos lê, por meio dos serviços `@Remote` `smartProvider.cost()` / `costDetail()` (`lib/remote.js`), a agregação feita por `lib/cost-stats.js` sobre o `cost.jsonl` real (total gasto / gratuito / pago / falhas / por provedor) — não são estimativas fictícias; a tabela de detalhe traz os seis campos de latência e as colunas ttft / tok-s, a tendência de custos é agrupada por **dia natural local**, e a página de configuração também mostra provedores/modelos reais e nomes de credenciais do pi-ai.

- **O controle nativo de intensidade na conversa agora aparece (versão 2026-11-28).** `lib/tier-ids.js::virtualReasoningDeclaration()` declara seis níveis de `reasoning.efforts` (`auto` + Desligado `off` / Baixo `low` / Médio `medium` / Alto `high` / Máximo `max`, `auto` por padrão); `lib/adapter.js` acrescenta o campo `reasoning` às entradas smart em `listModels`/`resolveModel`, satisfazendo a condição do host `reasoning !== undefined` em `ModelSelect.tsx:498` — a linha nativa de Effort aparece e o usuário pode escolher o nível no mesmo local dos demais modelos. `auto` abrange `off`: o nível padrão omite o parâmetro e é decidido dinamicamente conforme modelo e tarefa; um nível manual não suportado pelo primeiro salto (o salto gratuito só suporta `off`) é degradado para o nível válido `off`, em vez de enviar um nível alto não suportado. Os nomes nativos de effort seguem o codec do host (`z.string()`): chinês na interface zh, fallback em inglês nas demais línguas; as chaves em 7 idiomas `virtualEffort.*` da página de configurações permanecem intactas. A redação anterior, de que o controle nativo ficava oculto e a intensidade só era definida na página de configurações, está obsoleta; a cadeia de roteamento e o primeiro salto não mudam. Veja `SPEC-2026-11-27-smart-provider.md` §7.1.

## Instalação

A unidade de instalação é um pacote (bundle): o mercado instala o pacote npm público `dsh-smart-provider` (npm-first); para desenvolvimento local, `dsh plugin --profile <profile> add link:<este diretório>` (ou «Adicionar plugin» na interface) trata juntos dependências, seleção do pacote e a linha de patch. Um diretório local é salvo como `link:`, então alterações no código valem sem reinstalar; a desinstalação é `remove dsh-smart-provider`. Após a ativação, o log do host deve mostrar `registered smart adapter with N chain keys` e `discovered N neutral auto hop(s)`. Contrato de execução: apenas o serviço `llm` é obrigatório; os pacotes DSH são resolvidos por âncoras de manifesto, de modo que um pacote vinculado funciona em qualquer perfil.

## Configuração

`chains`, `accounts`, `ranking` e `ranking.routing` são configurações volatile; as alterações feitas na página de configuração têm efeito imediato, sem reinício. A configuração de routing fica aninhada em `ranking.routing` (schema.js:62-67), com os campos: `enabled` / `strategy` / `tierPolicy` / `weights` / `positionOverrides` / `tierLimit` / `longContextTokens` / `dynamicAuto`. Sem configuração explícita, o host injeta o roteamento padrão (`enabled:true` / `balanced` / quatro fatores em .25); somente com `ranking.routing.enabled !== true` explícito ou `null` o caminho segue byte a byte o modo legacy. Uma chave `chains` explícita e `*` sempre têm prioridade sobre `dynamicAuto`, de modo que configurações antigas não mudam de forma inesperada. Cada item do pool de contas `accounts` tem a forma `{id, provider, credentialRef, models[]}`; quando omitido, o modo antigo por salto continua em vigor. Rotas personalizadas só são declaradas em `registry/custom-routes.user.yaml` (`credentialRef` contém apenas um nome de referência, nunca uma chave em texto claro).

A justificativa detalhada está em três documentos do diretório de trabalho pai: `meta-provider-设计方案.md`, `多账号池设计方案.md`, `方案盲点审查.md`.

## Resumo (secundário)

Um meta-provedor registrado como a rota `smart`, **instalado e habilitado no ambiente de desenvolvimento deste projeto** (novos usuários devem verificar seu próprio perfil); o padrão interno do plugin é o modelo virtual «Inteligente» (`smart`) com intensidade `auto`, enquanto o padrão da sessão do host agora está aplicado ao modelo virtual «Inteligente» (`agent-default-model` = `provider: smart` / `model: smart`, id de catálogo de segmento único; intensidade via `defaultEffort`, padrão `auto`; `smart/auto` é apenas um id combinado interno, não um valor de perfil). É um roteador inteligente geral (custo / velocidade / capacidade / composto), neutro por padrão no código; priorizar economia é uma configuração opcional do usuário. Verificado: o modelo virtual «Inteligente» (`smart`) com intensidade `auto` em sessões reais (4 modelos virtuais, 6 níveis de intensidade, 4 entradas de catálogo de segmento único mais a configuração `defaultEffort`; `auto` é inclinação dinâmica, não mapeamento fixo; nomes via chaves locale em 7 idiomas), primeiro salto gratuito `x-opencode-free` (cost=0, 213+ linhas reais de ledger) com fallback 402→pago, página de configuração com recursos reais do pi-ai, aba de custos com ledger real via `@Remote` e uma visualização somente leitura da posição dos modelos (nota estática de quatro regras mais uma tabela de posições reais por modelo da nova projeção Host `@Remote modelPositions()`, dados ilegíveis mostrados como «não confirmado» e correções manuais ainda por arquivos de configuração), adaptação de recursos P1 e roteamento de duas camadas P2 ativo por padrão (`ranking.routing.enabled=true`, 8 predefinições, byte a byte legacy quando desativado). A configuração completa e os comandos de verificação estão no README do pacote.
