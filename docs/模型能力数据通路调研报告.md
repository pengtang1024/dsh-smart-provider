## 0. 一句话结论

**「原样暴露」不成立**：当前 DSH 的 `session/modelCatalog()` 上游 contract 只投影 `id/name/description/reasoning{efforts}/badge`，**根本没有 `contextWindow`、`input/inputModalities`、`tool` 三个字段，且 `reasoning` 是 efforts 对象而非布尔值**；前端 `client.js:2959` 虽只保留 `{id,name,group}`，但被丢弃的字段里没有 `derivePosition()` 所需的任何能力字段。因此**方案 A（前端拿 catalog 能力字段自己算）不可行**；唯一确定可走的路线是**方案 B：在 Host 侧新增一个 `@Remote` 方法，把真实能力字段显式映射后调用 `derivePosition()` 返回逐台定位表**。

### 2.2 Host 侧真实字段形状（来自 `app.asar` 打包源码，只读扫描）

> 以下证据来自 `/Applications/DSH NEXT.app/Contents/Resources/app.asar`（只读 mmap 扫描）。asar 内是打包源码，不是工作区文件，故用 **包名 + 源文件行号（打包源码自报 `sourceLocation`）/ 类型声明原文** 定位，而非工作区 file:line。

1. **`LlmModelInfo`（`listModels()` 返回项）**
   `packages/llm/llm/src/index.ts`（asar 内声明原文）：
   ```ts
   export interface LlmModelInfo {
     provider: string; id: string; name: string;
     description?: string;
     inputModalities?: readonly ModelModality[];  // 'text' | 'image'
     badge?: LlmModelBadge;
   }
   ```
   → **没有 `contextWindow`，没有布尔 `reasoning`，没有 `tool`，字段名是 `inputModalities` 而非 `input`。**

2. **`LlmResolvedModelInfo`（`resolveModelInfo()` 返回项）**
   ```ts
   export interface LlmResolvedModelInfo extends LlmModelInfo {
     context?: { contextWindow: number };
     defaultMaxTokens?: number;
     reasoning?: { efforts: readonly LlmReasoningEffortInfo[]; defaultEffort?: ReasoningEffortId };
     systemPromptUpdate?: SystemPromptUpdate;
     toolUpdate?: ToolUpdate;
   }
   ```
   → `contextWindow` 在 **`context.contextWindow`**；`reasoning` 是 **efforts 对象**，不是 `true`；`toolUpdate` 是「工具 schema 更新策略」，不是「是否支持工具」的布尔能力。

3. **`llm/discoverModels`（唯一带窗口的 Remote，asar `packages/llm/llm/src/index.ts:658`）**
   strict codec 原文：`{id, name?, contextWindow?: number, maxTokens?: number, inputModalities?: ('text'|'image')[]}`。
   pi-ai 实现（`dsh-llm-pi-ai/src/discovery.ts`，asar 内）：catalog 路由直接返回 `{id,name,contextWindow,maxTokens,inputModalities:[...model.input]}`；非 catalog 路由需 `baseURL`  interrogate endpoint。
   → 有 `contextWindow`/`inputModalities`，**仍无布尔 `reasoning` 与 `tool`**。

4. **pi-ai 适配器 `listModels()` / `discoverModels()` 实现**（asar，`dsh-llm-pi-ai`）
   - `listModels(provider)`：`snapshot.models.getModels(provider).map(model => ({provider,id,name,inputModalities:[...model.input]}))`
   - `discoverModels(request)`：catalog 路由返回 `{id,name,contextWindow,maxTokens,inputModalities}`
   → 插件 `adapter.routes` 里条目的真实字段更接近 `inputModalities`；`derivePosition` 读的 `input` **在真实数据上不会命中**（除非用户数据恰好用了旧字段名，而 Host 层会把它映射成 `inputModalities`）。

5. **`llm` namespace 暴露给客户端的 Remote 方法**（asar `createTypertRemoteInfo`，`@deepseek-ai/dsh-llm`）：只有 `llm/discoverModels`、`llm/listConfigurableProviders`、`llm/listProviders`。**`llm/listModels` 与 `llm/resolveModelInfo` 虽然有签名（`@Remote` 注释可见于 asar 的 TYPERT model 元数据），但不在 `$remote` 方法表里**——客户端不能直接调它们拿能力。

### 2.3 字段命名/形态不一致汇总（核心风险）

| `derivePosition` 期望 | 当前 Host 真实数据 | 直接后果 |
|---|---|---|
| `reasoning: true`（布尔） | `reasoning: {efforts:[...], defaultEffort?}`（对象）或 undefined | `reasoning === true` 永远为 false → **推理档永不自动命中** |
| `contextWindow: number`（顶层） | `context.contextWindow`（`resolveModelInfo`）/ `contextWindow`（`discoverModels`）/ `listModels` 无此字段 | 大部分 `route.models[]` 条目无顶层 `contextWindow` → **longctx 档不稳定** |
| `input: ['image']` | `inputModalities: ['image']` | `asArray(src.input)` 为空 → **vision 档永不自动命中** |
| `tool !== false` | 无 `tool` 字段（有 `toolUpdate`，语义不同） | 恰好走到默认分支 → 所有条目都会拿到 `tool`（保守但信息量为零） |

这一不一致解释了为什么 `docs/通用智能路由能力设计.md:59,76-82` 与 `docs/两层智能路由设计.md:42,46-54` 依据的是 **pi-ai SDK 旧类型 `Model.input/reasoning/contextWindow`（types.d.ts:653/667/675）**，而当前 Host 类型已是 DSH 自己的 `LlmModelInfo/LlmResolvedModelInfo`。设计文档的前提已经过时。

### 3.4 结论（明确回答任务 3）

- **不是「前端显式丢弃了能力字段」**：`client.js:2959` 丢弃的是 `description` / `reasoning{efforts}` / `badge`；这三个里**没有任何一个是 `derivePosition()` 需要的能力字段**。

## 4. `@Remote` / pi 快照是否可复用

### 4.1 `@Remote` 现状

- Host 方法清单：`lib/remote.js:323-337` marker 冻结了 7 个方法：`cost / costDetail / availabilityStatus / probeModels / accountHealth / statsSince / clearStats`。**没有模型能力或定位方法**。

- 源级守卫：`test/remote-surface.test.mjs:37` 冻结了这个方法清单，新增方法必须同步更新 marker、constructor reader、client descriptor 和该测试常量。
- Host `llm` Remote 只暴露 `listProviders / listConfigurableProviders / discoverModels`（§2.2.5）——`discoverModels` 有 `contextWindow`/`inputModalities`，但**需 settingsNs + 请求参数（baseURL/provider）、可能走网络 interrogate，并且没有布尔 reasoning 或 tool**；它不是逐台定位快照，复用它会把 UI 读变成探测请求，不符合「只读展示」。

**结论：现有 `@Remote` 没有可复用的逐台定位通道；pi 快照也没有。**

### 4.2 pi 快照现状

- 前端 `pi` state（`client.js:2769,2952-2973`）只有 `providers[{id,name}]` 与 `models[{id,name,group}]`。
- `session.modelCatalog()` 即使把 `reasoning` 带过来也只是 efforts 列表，无法映射到 `reasoning === true`；`badge` 是展示用标签（`LlmModelBadge.text/tone`），不是能力。
- `contextWindow` 只在 Host `resolveModelInfo` / `llm/discoverModels` 里存在，且都不在客户端可调用面。

**结论：复用 pi 快照只能得到「模型清单」，拿不到能力画像；不能支撑真实定位表。**

## 5. 可行方案清单与改动面

### 方案 A — 前端从 `session.modelCatalog()` 拿原始能力字段，自己算定位

- **可行性：❌ 已证伪（本次实测）**。上游 strict codec 无 `contextWindow`/`input`/`tool`，`reasoning` 是 efforts 对象；`client.js` 无 `derivePosition`，客户端也装不了 `lib/routing.js`（`client.js:558-562` 明说浏览器模块表无法解析本地 ESM，只能内联常量）。
- 若强行要做，需要改：DSH Host 的 session-controller（不在本仓库）+ wire codec + 客户端 strict schema + 内联一份 `derivePosition`。**跨仓库、影响面最大，且不属于插件可独立交付范围。**
- 结论：**不采用**。

### 方案 B — Host 新增 `@Remote` 方法返回逐台定位表（推荐）

- **可行性：✅ 唯一确定可落地的路线。** 数据都已在 Host 侧进程内，不需要新网络探测、不需要改 DSH 本体。
- 需改文件（本仓库内）：
  1. `lib/routing.js` — 新增一个**纯投影函数**，例如 `projectModelPositions({routes, overrides, longContextTokens})`：把真实字段显式映射成 `derivePosition` 期望的形状（`inputModalities→input`、`context.contextWindow→contextWindow`、`reasoning.efforts.length>0→reasoning:true`、`tool` 保持默认或按 `toolUpdate` 语义谨慎判定），逐条调 `derivePosition(m, override)`，返回 `{provider,id,name,tags,source,capabilities,evidence}`；不修改现有 `derivePosition`。
  2. 新建 `lib/position-snapshot.js`（或并入现有纯函数模块）— 只读快照构造 + 降级空表，风格对齐 `lib/health-snapshot.js:260-273`（失败返回 `{enabled:false, rows:[]}`，绝不抛）。

### 方案 C — 复用 `llm/discoverModels` / pi 快照做轻量展示

## 6. 关键不确定点（诚实标注）

1. **`adapter.routes` 的真实条目是否含顶层 `contextWindow`**：插件代码与测试都预期可能有（`lib/adapter.js:366-373`、`test/compaction.test.mjs:46`），但 Host `LlmModelInfo` contract 不含此字段；pi-ai `listModels` 实测源码也不含。真实 profile 里是否因某条路径补上，**本次只读调研无法确认**；方案 B 必须同时兼容「有/无顶层窗口」并明确标注「未确认」。
2. **生产环境 `derivePosition` 的实际输出**：按 §2.3 的字段错配推断，当前运行期 `positions` 很可能绝大多数只有 `[tool, general]`，即两层路由的位置筛选实际退化为兜底；**这是强推断，未用真实会话日志验证**。若要定案，需另做一次运行期只读日志/探针（本次任务范围外）。
3. **`reasoning` 代理规则**：`reasoning.efforts` 非空（或含非 `off` effort）是否等价于 `reasoning === true`，属于产品口径决定，不是代码事实；会影响表中推理档的真实性。
4. **`tool` 档语义**：Host 的 `toolUpdate` 不等于「支持工具」；`derivePosition` 的 `tool !== false` 只是保守默认。表中应写「默认具备（未声明不支持）」，不要写成实测能力。
5. **`session.modelCatalog()` 的 `description`/`badge`** 虽被前端丢弃，但与定位无关；若产品还要展示展示名/徽标，可顺手保留，属独立需求。
6. **asar 证据的定位方式**：§2.2/§3.2/§3.3 的证据来自只读扫描 `app.asar` 打包源码（含 TS 原文与 generated strict codec），不是工作区 file:line；版本为当前安装的 DSH（v2.8.1 插件所运行的宿主）。升级 DSH 后须重新核对 contract。
7. **本报告未跑任何测试/构建/git 写操作**，所有结论均为静态只读证据；`test/*` 的引用只是阅读源码，未执行。
